## 1:30 C# 會怎麼寫（為什麼在 Go 行不通）

【畫面】左邊 Visual Studio：`ProductNotFoundException : Exception`、`throw new ProductNotFoundException(id)`，再來是 `app.UseExceptionHandler(...)`。

> 如果是 C# 的朋友，這個下午你會這樣過：
> 寫一個 `ProductNotFoundException`，在 service 裡 `throw`。
> 然後在管線最外面掛一個全域的 exception handler：`catch` 到什麼，就轉成什麼 JSON。
> 所有錯誤的出口只有一個，格式自然一致。真的很優雅。

> 當然，這個設計我用了很多年，它很有效。可是它有個代價：**錯誤是隱形的**。
> 你看一個方法的簽名：`Product GetProduct(int id)`。它會失敗嗎？會丟什麼？不知道。簽名什麼都沒說，你得去讀實作，還得去讀實作呼叫的實作。
> 於是你只能在最外面接一個網，什麼都接。接到一個 `NullReferenceException` 的時候，你要回 404 還是 500？這說明什麼？說明網子太大，什麼魚都撈得到。

> Java 的朋友多一個選擇題：checked exception。簽名上寫明會丟什麼，聽起來很誠實。結果大家一路 `throws Exception` 往上推，最後變成什麼都寫了，等於沒寫。

【畫面】Go 版簽名：`func (s *ProductService) Get(ctx context.Context, id int) (Product, error)`。

> Go 的做法：**錯誤就是回傳值**。看簽名，最後一個回傳值是 `error`，它在告訴你：這個函式會失敗，你得面對它。
> 面對的方式很樸素：`if err != nil`。
> 對，會寫很多次。我自己也覺得煩。可是你想想：每一個可能失敗的地方，都有一行字擺在你眼前，沒有任何一個錯誤是從天花板掉下來的。
> 那問題來了：沒有 `catch`，我要怎麼分辨「找不到」跟「資料庫掛了」？好那我們來看。

## 3:45 第一段：OpenAPI 契約先行（先決定錯誤長什麼樣）

【畫面】`api/openapi.yaml`，捲到 `components/schemas/Error`。

```yaml
Error:
  type: object
  required: [code, message]
  properties:
    code:    { type: string }   # 給程式看，不會變
    message: { type: string }   # 給人看，可以改
    field:   { type: string }   # 哪個欄位錯了（可選）
```

> 前端抱怨的根本原因，是我們沒有契約。所以這集第一步，不寫程式，寫一份 OpenAPI。
> 看這個 `Error`：`code` 是給程式 `switch` 用的，永遠不改；`message` 是給人看的，想怎麼改都行；`field` 告訴你是哪個輸入錯了。
> 注意每支 API 的 `default` 回應，全部指到同一個 `Error`。**這份契約說了：不管哪支 API、不管哪種錯，長這樣。**

【畫面】終端機 `make api`，檔案樹長出 `internal/api/api.gen.go`；打開第一行。

> 然後跑 `make api`。oapi-codegen 讀契約，產生 `api.Error`、`api.Product`，還有一個 `ServerInterface`。
> 注意第一行：`Code generated … DO NOT EDIT.` 這種檔案我們不改，要改就改契約再重新產生。跟第 2 集的 sqlc 同一個精神，只是這次來源是 YAML，不是 SQL。
> C# 的朋友可能會想到 NSwag 或 Swashbuckle。方向相反：它們通常是程式碼先寫好、再吐出文件；我們是文件先寫好、再長出程式碼。文件不會過期，因為它是源頭。

【畫面】`internal/handler/handler.go`，圈出 `var _ api.ServerInterface = (*server)(nil)`。

> 看這一行，這是 Go 的老招式：把 `server` 指給 `ServerInterface`，只為了讓編譯器檢查。
> 契約多了一支 API，我們沒實作，**編譯就紅字**。契約不是裝飾，是被編譯器盯著的。

## 5:45 第二段：error 是值，sentinel 與型別化錯誤

【畫面】`internal/service/errors.go`。

```go
var ErrProductNotFound = errors.New("product not found")

type ValidationError struct {
    Field   string
    Message string
}

func (e *ValidationError) Error() string { ... }
```

> 好，怎麼分辨「找不到」跟「別的錯」？Go 給你兩種樸素的做法。
> 第一種，**哨兵錯誤**：宣告一個全域的值，`ErrProductNotFound`。它就是一個值，用 `errors.New` 做出來，誰要判斷，誰就拿它來比。
> 第二種，**型別化錯誤**：自己定義一個型別，這裡是 `ValidationError`，身上帶著 `Field` 跟 `Message`，只要有 `Error() string` 這個方法，它就是一個 `error`。
> 前者像 C# 的 `ProductNotFoundException` 當標記；後者像帶欄位的自訂 exception。差別是：它們全是普通的值，沒有繼承樹、沒有 `throw`，只是被回傳。

【畫面】`internal/service/product.go` 的 `Get`。

```go
return Product{}, fmt.Errorf("get product %d: %w", id, ErrProductNotFound)
```

> 看這一行，這集最重要的一個字元：`%w`。
> 一般的 `%v` 只是把錯誤變成一段字，原本的錯誤就丟了。`%w` 是**包起來**：我們加一句脈絡，「get product 99」，同時把原本的錯誤留在裡面。
> 它像一個一層一層的信封。外面寫著「是誰在做什麼」，打開來，裡面還是原本那個錯誤。
> 以前 C# 的 `InnerException`，你可能很熟。這裡是同一個概念，只是它不是掛在 exception 上的屬性，是 `fmt.Errorf` 的一個動詞。

【畫面】`internal/handler/errors.go` 的 `writeError`，逐行圈出 `errors.Is`、`errors.As`。

```go
switch {
case errors.Is(err, service.ErrProductNotFound):
    ...404
case errors.As(err, &validation):
    ...400
case errors.As(err, &badParam):   // 生成碼的綁定錯誤，例如 /products/abc
    ...400
default:
    logger.Error("request failed", "err", err)
    ...500
}
```

> 然後是出口：`writeError`，我們接得到的錯誤回應，都從這裡出去。（程式直接 panic 的情況不在內，那要等第 4 集的 middleware 來接。）
> `errors.Is`：問「這個錯誤，不管包了幾層信封，裡面有沒有那個哨兵？」有，就是 404。
> `errors.As`：問「信封裡有沒有這個型別？有的話，把它交給我」，所以我們拿到 `validation.Field`，直接填進回應。
> 為什麼不直接寫 `err == ErrProductNotFound`？因為 service 把它包過了，外面看到的是「get product 99: product not found」，這個值跟哨兵**不相等**。這就是為什麼要用 `errors.Is`：它會一層一層拆信封來找。
> 都不是的呢？走到 `default`。我們把真正的原因記進 log，但回給客人的只有 `internal error` 這一句。資料庫連線字串那種東西，永遠不該長在回應裡。這個下面測試會證明。

## 8:30 第三段：把所有出口接到同一個地方

【畫面】`internal/handler/handler.go` 的 `New`。

```go
r.NotFound(notFound(logger))
r.MethodNotAllowed(methodNotAllowed(logger))
...
ErrorHandlerFunc: func(w http.ResponseWriter, _ *http.Request, err error) { writeError(w, logger, err) },
```

> 好，前端看到的三種怪格式，原因其實各不相同，所以我們要堵三個洞。
> 第一個：我們自己的 handler。以前它自己 `http.Error` 吐純文字；現在不寫了，全部丟給 `writeError`。
> 第二個：路由器。chi 找不到路由時，預設回一行 `404 page not found`；方法不對時，預設回空白。這兩個就是前端說的「純文字」跟「什麼都沒回」。我們把兩個預設換成自己的，一樣吐 `api.Error`。
> 第三個最陰險：**生成的程式碼**。`/products/abc`，`abc` 不是數字，這個錯在我們的 handler 被呼叫之前就發生了，由 oapi-codegen 產生的那層攔下來。它的預設是回純文字。所以我們在選項裡掛一個 `ErrorHandlerFunc`，讓它也走 `writeError`。
> 三個洞，一個出口。你說，這個設計難道不吸引你嗎？

> 順手交代一件事：`/healthz` 我們沒放進契約。它是給負載平衡器看的探針，不是給前端的 API，回 `ok` 就夠了。

## 10:15 證明：每一種壞法，都是同一個形狀

【畫面】`internal/handler/handler_test.go`，圈出 `TestErrorResponsesShareOneShape`。

> 光說不練，是 PowerPoint 工程師。這集的事故是「格式不一致」，所以我們的測試，名字就叫 `TestErrorResponsesShareOneShape`。
> table-driven：每一列是一種壞法。找不到、`%w` 包了兩層的找不到、id 是 `abc`、id 是 0、列表壞掉、單筆壞掉、不存在的路由、錯的方法，一共八列。
> 每一列都檢查同樣幾件事：`Content-Type` 是 JSON；body 能 decode 成 `api.Error`，而且**不能有多餘的欄位**，我們用 `DisallowUnknownFields`；`code` 是預期的值；`message` 不是空的，也不能洩漏 `postgres://` 這種字串。

【畫面】`go test ./...` 全綠；接著再跑 `curl localhost:8080/products/999`、`/products/abc`、`/nope`，三個回應並排，都是 `{"code": ..., "message": ...}`。

> 綠燈。再用真的 server 打一次：找不到、格式錯、路由不存在，三種完全不同的壞法，長得一模一樣。
> 前端的同事只需要一個 `switch (error.code)`。

## 11:45 三點收尾

> 好，我們收一下。
> **第一**，Go 沒有 exception，錯誤是回傳值。簽名最後一個 `error` 就是誠實的警告；`if err != nil` 很煩，但每個失敗都擺在你眼前。
> **第二**，用 `%w` 包裝，加脈絡但不丟掉原因；在邊界用 `errors.Is` 比哨兵、用 `errors.As` 取型別化的錯誤。不要用 `==`，因為信封會讓它失效。
> **第三**，契約先行：OpenAPI 說了錯誤長什麼樣，oapi-codegen 產生程式碼，所有出口，包括路由器跟生成碼的錯誤，都接到同一個 `writeError`，再用一支測試鎖住。
>
