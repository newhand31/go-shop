## 1:40 C#／Java 會怎麼寫（為什麼在 Go 行不通）

【畫面】左邊 ASP.NET Core：`Host.Run()`，Ctrl+C 之後 Kestrel 停止接新連線、等進行中的請求，`IHostApplicationLifetime` 有 `ApplicationStopping`。右邊 Spring Boot：`server.shutdown=graceful`，加 `spring.lifecycle.timeout-per-shutdown-phase`。下面是我們的 `main.go`，只有一行 `srv.Close()`。

> C# 的朋友，`Host.Run()` 收到 SIGTERM 之後，主機會停止接新連線、等進行中的請求，還有一個逾時可以調；你想在關機前做點事，掛到 `IHostApplicationLifetime`。Java 的朋友，Spring Boot 要設 `server.shutdown=graceful`；老實說，Spring 的預設值是立刻關。所以被砍到客人的，不只有我們。
> 但這兩邊有一個共同點：**順序是框架排的。** 你只是在它排好的流程裡掛幾個勾子。
> Go 的標準庫沒有主機，也沒有流程。`http.Server` 只給你兩個零件：`Close`，立刻砍掉所有連線；`Shutdown`，關掉入口、等進行中的請求。要用哪個、什麼時候用、背景那些 goroutine 排在前面還是後面，沒有人替你決定，因為 `main` 就是那個主機。
> 這很麻煩，而且**我們上一集那一行 `srv.Close()`，就是選了錯的零件。**

## 3:30 第一段：訊號，SIGTERM 才是 Docker 的口頭禪

【畫面】`cmd/api/main.go` 第 102 行。

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
```

> 第一個問題：我們怎麼知道要關了？作業系統用訊號通知。你在終端機按 Ctrl+C，是 `os.Interrupt`。但 `docker stop`、Kubernetes 的部署，送的是 `SIGTERM`。我們之前只聽 Ctrl+C，所以在本機測試永遠沒問題。上了容器，`SIGTERM` 寄到一個沒登記要收它的 Go 程式，預設動作是直接結束：程式當場消失，進行中的請求跟著斷線。至於 Docker 那個「十秒」，是另一回事：它是程式有接到訊號、卻遲遲不結束的時候，Docker 最後送 `SIGKILL` 之前願意等的時間，`SIGKILL` 沒辦法接。
> `signal.NotifyContext` 好用的地方是：它回傳一個 `ctx`，訊號一到就被取消。接下來整個關機流程，只要等 `ctx.Done()`。
> 還有一個要記住的：**`ctx` 在這裡的意思是「不要再接新請求」，不是「所有東西都停」。** 這一點，第三段會用到。

## 4:30 第二段：`Shutdown`，還有一個很會騙人的錯誤值

【畫面】`internal/platform/lifecycle/lifecycle.go` 第 21 行起的 `Serve`。

```go
go func() { serveErr <- srv.Serve(ln) }()
select {
case err := <-serveErr:
    return fmt.Errorf("serve: %w", err)
case <-ctx.Done():
}
shutdownCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), grace)
defer cancel()
if err := srv.Shutdown(shutdownCtx); err != nil {
    _ = srv.Close() // 時間到：剩下的砍掉
    ...
}
```

> `srv.Shutdown(ctx)` 做的事：馬上關掉監聽的 port，不再有新連線；已經進來的請求，讓它們跑完；全部做完，函式才回來。`ctx` 是「最多等多久」，等到了就回錯誤，我們再用 `Close` 砍剩下的。
> 兩個細節。第一，傳給 `Shutdown` 的不能是那個已經被取消的訊號 `ctx`，不然它第一行就放棄了；所以我們用 `context.WithoutCancel` 拿一個乾淨的、再加一個倒數計時。
> 第二個，**很會騙人：** 你一呼叫 `Shutdown`，`srv.Serve` 就**立刻**回傳 `http.ErrServerClosed`。這個錯誤的意思是「我開始打烊了」，不是「我打烊完了」。如果你的 `main` 看到它就收工，那進行中的請求，會在你眼前被一起收掉。**這就像餐廳把門口的牌子翻成「已打烊」，然後老闆就回家了，廚房裡還有六桌的菜。** 所以我們等的是 `Shutdown` 自己回來，不是 `Serve`。

> 當然，等多久要有上限。我們設 25 秒，可以用 `SHUTDOWN_GRACE_SECONDS` 改。為什麼是 25？下一段講。

## 5:45 第三段：順序，背景 goroutine 要排在伺服器後面

【畫面】`cmd/api/shutdown.go` 的 `serveThenStop`，和 `main.go` 第 174 行起。

```go
workers := lifecycle.NewGroup()
defer workers.Stop()
workers.Go(dispatcher.Run)
workers.Go(janitor.Run)
workers.Go(sale.Run)
...
err = serveThenStop(ctx, srv, ln, grace, workers)
```

> 現在我們有三個背景 goroutine：寄信的、清過期訂單的、搶購的 worker。上一集它們的 context 是從訊號 `ctx` 長出來的，所以 Ctrl+C 一來，它們跟伺服器**同時**收到「停」。
> 想一個情境：搶購的 worker 只有一個，它正在寫客人 A 的訂單，客人 B 的請求已經被接受了，在佇列裡排隊。這時候訊號來了。如果 worker 馬上停，B 的請求還活著、連線還開著，卻再也沒有人處理它，只會得到一個 503。**這就像門牌翻成已打烊的同時，廚師也跟著下班，客人的菜就擺在出菜口。**
> 所以順序是：先排空伺服器，**然後**才停 worker。我們寫了一個很小的 `lifecycle.Group`：它的 context 不是從訊號長出來的，只有呼叫 `Stop` 才被取消；`Stop` 取消之後會等每一個 goroutine 都回來。`serveThenStop` 就兩行：先 `Serve`，再 `workers.Stop()`。
> 回頭看 `main` 的 `defer`：它們是反著跑的。`serveThenStop` 回來之後，先是 `workers.Stop()` 那個 defer（已經停過了，再呼叫一次沒事），然後 Redis 關、資料庫連線池關、最後才把還沒送出的 span 沖掉。**誰用到誰，誰最後關。**
> 還有一個數字：伺服器最多排空 25 秒，加上 span 沖出去最多 5 秒，所以 compose 裡的 `stop_grace_period` 設 40 秒。Docker 預設只等 10 秒，不調的話，我們的優雅關機，會在中途被 `SIGKILL`。

## 7:30 第四段：Dockerfile，多階段、scratch

【畫面】`Dockerfile`。

```dockerfile
FROM golang:${GO_VERSION}-alpine AS build
...
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/api ./cmd/api

FROM scratch
COPY --from=build /out/api /api
USER 65532:65532
ENTRYPOINT ["/api"]
```

> 關機會了，我們來把它放進容器。C# 或 Java 的朋友，你的 image 裡一定有 runtime：JRE、.NET runtime，加上作業系統的一堆東西。Go 編出來的是一個靜態二進位，沒有 runtime 要帶，連資料庫 migration 都已經用 `embed` 包在裡面。所以最後那個 image，可以是 `scratch`：**真正的空。**
> 兩階段的意思：第一階段有完整的 Go 工具鏈，用來編譯；第二階段只把編好的檔案拷過去。工具鏈、原始碼、模組快取，一個都不會出貨。`go.mod` 和 `go.sum` 先拷，是為了讓「下載依賴」這一層可以被快取，改一行程式碼不用重新下載全世界。
> `CGO_ENABLED=0` 是這份 Dockerfile 要說出口的一行：scratch 裡面沒有 libc，動態連結的二進位一啟動就說「找不到檔案」，那個檔案明明就在。老實說，`golang:alpine` 裡沒有 C 編譯器，cgo 本來就會是關的；我們還是寫出來，讓建置不依賴 base image 的脾氣。**scratch 有多空？沒有 shell、沒有 `ls`、沒有 `curl`。出事想進去看看？看什麼，看二進位檔嗎？**

## 9:00 這些設計決定，各自為什麼

【畫面】`Dockerfile` 最後幾行；`docker-compose.yml` 的 `api` 服務。

> 幾個刻意的決定。
> 第一，`ENTRYPOINT` 用**陣列寫法**，讓我們的程式自己當 PID 1，直接收到 `SIGTERM`。寫成 `ENTRYPOINT /api`，Docker 會包一層 `/bin/sh -c`：在 scratch 裡根本沒有 shell，容器連啟動都不會成功。**這是少數一種錯，會在第一秒就大聲告訴你。** 但如果是有 shell 的 image，同樣的寫法會讓 `sh` 當 PID 1，`SIGTERM` 送給 `sh`，而 `sh` 不一定轉給你：訊號寄到了，只是寄給了櫃檯，不是主廚。這個坑，在你換 base image 的那天會等著你。
> 第二，`USER 65532`，一個純數字：scratch 沒有 `/etc/passwd`，沒有名字可以查，而且不用 root。
> 第三，**沒有 `HEALTHCHECK`**。因為健康檢查要執行一個指令，scratch 裡沒有東西可以執行。這不是忘了，是取捨：讓平台自己去探 `GET /healthz`。
> 第四，我們從 `.dockerignore` 把 `.git`、文件、腳本全擋掉，編譯的時候，不會把整個專案的歷史拷進去。
> 最後，compose 裡的 `api` 服務放在 `app` 這個 profile 後面，平常 `docker compose up` 還是只有資料庫；要跑整個商店，加 `--profile app`。

## 10:00 證明：進行中的請求做完，排隊的客人不被丟掉

【畫面】`go test ./internal/platform/lifecycle ./cmd/api -v`，全綠。

> 證明兩件事。第一，進行中的請求真的做完。測試啟一個伺服器，handler 卡在一個 channel 上；請求進來之後，我們取消訊號 `ctx`：`Serve` **沒有**回來。接著放開 channel，客人收到完整的回應，然後 `Serve` 才回來，而且回傳 `nil`。另外一個測試證明：關機開始之後，新的連線被拒絕；時間到了還沒做完，連線被砍掉，錯誤裡有 `context.DeadlineExceeded`。
> 第二件，排隊的搶購客人沒有被丟掉。測試用的是 `main` 同一組呼叫：`lifecycle.Group` 加 `serveThenStop`。一個 worker，客人 A 卡在資料庫，客人 B 排在佇列。訊號來了，放開 A：**兩位都收到 201。** 如果把 `serveThenStop` 裡的兩行對調，這個測試會紅。
> 還有一個測試只是讀 Dockerfile 文字：最後一階必須是 `FROM scratch`，`ENTRYPOINT` 必須是陣列寫法，編譯必須有 `CGO_ENABLED=0`。**它不編譯 image**，所以它只是守住這三行，不證明 image 可以啟動。

## 11:45 三點收尾

> 好，我們收一下。
> **第一**，關機是一段流程：先停止接新請求，再讓進行中的請求做完，再停背景 goroutine，最後才關資料庫。`Serve` 回傳 `ErrServerClosed` 只代表「開始打烊」。
> **第二**，背景 goroutine 的 context 不要從訊號 `ctx` 長出來。它們要等伺服器排空，才有資格停。
> **第三**，容器：多階段編譯，`CGO_ENABLED=0`，scratch 當最後一階，`ENTRYPOINT` 用陣列寫法，讓你的程式收到 `SIGTERM`。
