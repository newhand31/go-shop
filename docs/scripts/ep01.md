## 1:30 C# 會怎麼寫（為什麼在 Go 行不通）

【畫面】左右分割：左邊 VS，右邊空的 Go 資料夾。

> 如果是 C# 的朋友，這個晚上你會這樣過：
> 打開 Visual Studio，File → New → ASP.NET Core Web API，按下建立。
> 好，三秒鐘，你已經有了：`Program.cs`、`appsettings.json`、一個範例 `WeatherForecastController`，還有 `builder.Services.AddScoped<IProductRepository, ProductRepository>()` 這一行。

【畫面】`Program.cs` 範例，圈出 `builder.Services.AddScoped`、`app.UseMiddleware<RequestLoggingMiddleware>()`、`app.MapControllers()`。

> 這一行是什麼意思？意思是「有人需要 `IProductRepository` 的時候，容器你去幫我找實作」。
> 誰會需要？Controller 的建構子。誰來 new Controller？框架。誰來 new 框架？……好，我們不追了，再追下去會追到宇宙大霹靂。
> 當然，這個設計沒有錯，大型專案裡它很好用。可是對一個要在今晚上線的人來說，它有個小問題：我們看不到誰 new 了誰。出事的時候，你在 debug 的是一棵你沒親眼看過的物件樹。

> 那 Go 呢？Go 沒有內建的 DI 容器，沒有 `Controller` 基底類別，也沒有範本專案精靈。
> 它給你的是：一個 `main` 函式，還有「自己 new」這個古老的技術。
> 這說明什麼？說明我們今晚要手動接線。聽起來很原始，好那我們來看，它其實比你想的舒服。

## 3:30 第一段：專案結構（`cmd/` 與 `internal/`）

【畫面】切到編輯器，展開檔案樹：`cmd/api/main.go`、`internal/handler`、`internal/service`、`internal/repository`、`internal/platform`。

> 好那我們先看資料夾。
> `cmd/api/`：這是程式的進入點，`main` 住在這裡。以後我們還會有 `cmd/worker/`，所以它是一個資料夾，不是一個檔案。
> `internal/`：這是 Go 編譯器強制執行的規則——放在 `internal/` 底下的套件，別的 module 不准 import。
> 這跟 C# 的 `internal` 關鍵字很像，但差別在於：C# 是類別層級，Go 是**資料夾層級**。想偷 import？編譯直接給你紅字。

【畫面】在另一個臨時 module 嘗試 import `github.com/newhand31/go-shop/internal/service`，終端機顯示 `use of internal package ... not allowed`。

> 底下三層是我們的分層，方向只有一個：**handler 呼叫 service，service 呼叫 repository**。
> handler 管 HTTP，service 管業務，repository 管資料。反過來呼叫？不行。跨一層呼叫？也不行。
> 這規則誰來守？目前是我，用我的自律。你看我這個人，連已讀都能拖到晚上 11 點，所以這個自律今晚先靠 code review 撐著，之後我們再看有沒有工具幫忙。

> 這一段重點：**資料夾本身就是設計**。Go 沒有 namespace 這種獨立的東西，資料夾就是套件，套件就是邊界。

## 5:30 第二段：手動組裝（沒有容器，就是 `main`）

【畫面】`cmd/api/main.go` 全螢幕，逐行停格。

```go
repo := repository.NewMemoryProducts()
svc  := service.NewProductService(repo)
h    := handler.New(svc, logger)
```

> 看這三行。
> 第一行，new 一個 repository。第二行，把它交給 service。第三行，把 service 交給 handler。
> 這就是整個「依賴注入」。它沒有名字，沒有框架，沒有 `IServiceCollection`。如果你問我生命週期是 Scoped 還是 Singleton？這裡只有一種：**你寫在 `main` 的那一種**。
> 建構子收什麼就是什麼，編譯器幫你檢查。少傳一個，紅字；傳錯一個，紅字。比起 C# 在執行期才爆出 `Unable to resolve service for type`，我寧願在晚上 11 點就看到紅字，而不是在早上 9 點。

【畫面】切到 `internal/service/product.go`，聚焦 `ProductStore` interface。

> 再看一個細節。service 需要資料，它怎麼拿？

```go
type ProductStore interface {
    List(ctx context.Context) ([]repository.Product, error)
}
```

> 注意，這個 interface **是 service 自己宣告的**，不是 repository 宣告的。
> C# 的習慣是：先寫 `IProductRepository`，放在 repository 那邊，然後實作它。Go 反過來：**誰要用，誰定義**，而且只列自己真的用到的方法。
> repository 這邊呢？

【畫面】切到 `internal/repository/product.go`。

> 它完全不知道有人要 interface。它只是有一個 `List` 方法，剛好對上了。這叫隱式滿足，沒有 `: IProductRepository`，沒有 `implements`。
> 這件事第 5 集我們還會再講，今天只要記住：interface 是使用端的需求清單，不是實作端的證件。
> 為什麼要這樣？因為明天之後我們要把記憶體換成資料庫。換的時候 service 一個字都不用改。（第 2 集預告，笑。）

## 8:00 第三段：chi 與 slog（兩個今晚要用的工具）

【畫面】`internal/handler/handler.go`。

> 路由我們用 chi。為什麼不用 Gin？因為 chi 的 handler 就是標準庫的 `http.Handler`，長得跟你以後在任何 Go 專案看到的一樣。你學到的是 Go，不是某個框架。

> 那 middleware 呢？C# 的朋友會想到 `app.UseMiddleware<T>()`，要一個類別、一個 `InvokeAsync`、一個 `RequestDelegate next`。
> Go 的 middleware 是什麼？

```go
func(next http.Handler) http.Handler
```

> 就這樣。一個函式，吃進一個 handler，吐出一個 handler。**函式包函式**。
> 我們的日誌 middleware 做三件事：記下開始時間、呼叫 `next`、記下方法、路徑、狀態碼和耗時。

【畫面】`RequestLog`，圈出 `statusRecorder`。

> 這裡有個小陷阱：標準庫的 `ResponseWriter` 沒辦法事後問它「剛剛回的是幾號狀態碼」。所以我們包一層，把 `WriteHeader` 偷看一眼再放行。
> 偷看，不是偷改。這很重要，因為偷改是下一個事故的名字。

【畫面】終端機 `curl localhost:8080/products`，另一個視窗跑出一行 JSON 日誌。

> 日誌用 `log/slog`，標準庫，輸出就是 JSON，每個欄位都是 key-value。
> 為什麼要結構化？因為半夜 3 點你不會想用眼睛 grep 一整面字，你會想用查詢。這一點，第 11 集會連本帶利還給你。

## 10:00 證明：測試與實際打一次

【畫面】`internal/handler/handler_test.go`。

> 光說不練，是 PowerPoint 工程師。我們用測試證明。
> Go 的測試預設寫法叫 table-driven：一張表，每一列是一個情境，一個迴圈跑完。

```go
{"healthz", GET, "/healthz", ..., 200},
{"products 空清單回 []", ..., 200},
{"products service 出錯", ..., 500},
{"products 不收 POST", ..., 405},
```

> 對 xUnit 的朋友來說，這就是 `[Theory]` 加 `[InlineData]`，只是不需要任何屬性，也不需要測試框架——`go test` 內建。
> 而且注意：測 handler 的時候，我們根本不用起伺服器。`httptest` 給你一個假的請求、一個假的記錄器，直接呼叫。快得不像話。

【畫面】跑 `go test ./...`，綠燈。接著 `go run ./cmd/api`，`curl /healthz`、`curl /products`。

> 好，綠燈。實際打一次：`/healthz`，回 200。`/products`，回三件商品。
