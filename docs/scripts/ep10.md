# 第 10 集｜雙 11 打爆 DB（口播稿草稿 v0）

- 目標長度：12–13 分鐘（約 3,500 字口播）
- 本集唯一主概念：**有容量上限的 channel 就是背壓**：用 Redis 預扣把「已經賣完」的人擋在資料庫外面，再用一條有固定緩衝的 channel 加 `select … default`，讓排隊排不下的人當場被拒絕，而不是在後面默默越堆越多。重點對照：`System.Threading.Channels` 的 `TryWrite`／Java 的 `BlockingQueue.offer`，和它們的「會等」版本 `WriteAsync`／`put` 之間的差別，就是「排隊」和「背壓」的差別
- 程式對應：tag `ep10`（`git checkout ep10`）
- 風格依 [style-guide.md](../style-guide.md)；【畫面】是剪輯提示，不唸出來。
- 笑點時間軸（規則 3：每 3–4 分鐘一個大笑點）：0:00／2:30／5:15／7:30／9:00／10:30，間距都在 3 分鐘內。

## 0:50 時間錨點開場

> 現在是雙 11 晚上 8 點 31 分，開賣三十一分鐘，資料庫連線池滿了，庫存剩下一台，而我們已經收到一萬九千筆「請稍候」。
> 今天做三件事：搶購的時候，先在 Redis 用一個計數器預扣庫存，賣完的人不用進資料庫；進得去的人，排進一條有長度上限的 channel，排不下就當場回「忙碌中」；最後，給資料庫連線池一個上限，同時進資料庫的 worker 比上限少。然後證明三件事：預扣不超賣、channel 滿了會拒絕、資料庫連線數有上限。
> 今天只學一個重點：**有容量的 channel，就是背壓。**

## 1:40 C#／Java 會怎麼寫（為什麼在 Go 行不通）

【畫面】左邊 Spring：`@Transactional` 的 `buy()`，前面一個 `ThreadPoolExecutor`，佇列是 `LinkedBlockingQueue`（沒設上限）；C# 版：`Channel.CreateUnbounded<Order>()`。右邊是空的 `flashsale.go`。

> Java 的朋友，你大概會說：丟給 `ExecutorService`，讓它排隊。C# 的朋友：`Channel.CreateUnbounded`，生產者寫，消費者讀。
> 它們都很好用，也都有一個預設值，讓這個晚上變成事故：**佇列沒有上限。** `LinkedBlockingQueue` 不設容量，預設是 `Integer.MAX_VALUE`；`CreateUnbounded`，名字就告訴你了。
> 沒有上限的佇列，不是解決問題，是把問題搬家。連線池的爆炸沒了，變成記憶體慢慢漲，每個排隊的請求都佔著一個連線、一個 goroutine 或執行緒、一個等著回應的使用者。三分鐘之後，使用者的等待時間從兩秒變成三分鐘。他們不會說「哇，好有耐心的系統」。他們會重新整理。
> **然後兩萬個人，變成四萬個人。** 我們的佇列很客氣，它一個都不拒絕。這是這個晚上最有禮貌的當機。

> 要修的不是讓佇列更快，是讓它有一個「滿了」的狀態，而且滿了要能說「不」。

## 3:30 第一段：Redis 預扣，賣完的人不進資料庫

【畫面】`internal/repository/flashsale.go`，圈出 `reserveScript`（第 20 行起）。

```lua
local left = redis.call('GET', KEYS[1])
if not left then return -1 end
if tonumber(left) < tonumber(ARGV[1]) then return 0 end
redis.call('DECRBY', KEYS[1], ARGV[1])
return 1
```

> 第一個想法：十台顯示器，兩萬個人，其中一萬九千九百九十個人，一定買不到。為什麼要讓他們每一個都進資料庫，鎖一下那一列，再告訴他們「沒了」？
> 所以在資料庫前面放一個計數器：Redis 的一個數字，十。每個人先來拿一個。拿得到，才有資格往下走；拿不到，立刻回「賣完了」，資料庫根本不知道有這個人。
> 重點是「拿」要怎麼寫。先 `GET`，看夠不夠，再 `DECRBY`？兩個指令，中間有空隙，兩個人同時看到「剩一個」，都扣，變成負的。這就是第 6 集的超賣，換了一個地方，繞了一個網路來回。
> 所以我們用 Lua 腳本。Redis 執行一支腳本的時候，中間不會插入別人的指令：檢查和扣除是同一個動作。回傳三種結果：-1 沒開賣、0 不夠、1 拿到了。
> 注意，Redis 的計數器只是一道閘門，**不是真相**。真相還是資料庫：訂單成不成立，由第 6 集那個 `FOR UPDATE` 的交易決定。計數器只負責一件事：把一萬九千九百九十個一定買不到的人擋在門外。

> 如果之後資料庫那邊失敗，預扣的那一個要還回去，這叫補償：`Release`，一個 `INCRBY`。
> 這是整個系列第一次，我們為了修一個 Go 專案的 bug，寫了一段不是 Go 的程式。好像有道理哦，Lua 住在 Go 專案裡，有點奇怪——不對，這支腳本住在 Redis 裡，我們只是把檢查和扣除這一個動作，請它一次做完。**我們沒有學 Lua，我們只是借了它十行。**

## 5:45 第二段：有上限的 channel，加 `select … default`

【畫面】`internal/service/flashsale.go`，`Buy`，圈出 `select`（第 106 行起）。

```go
select {
case f.queue <- job:
default:
    f.release(job)
    return Order{}, ErrBusy
}
```

> 預扣拿到的人，要進資料庫了。可是不能全部同時進去，那會把連線池打爆，所以中間放一條 channel：`make(chan *flashJob, 64)`，容量六十四。
> 一般的寫法是 `f.queue <- job`。這一行在 channel 滿的時候，**會停在那裡等**：goroutine 卡著，連線掛著，使用者的瀏覽器轉圈圈。這和 `CreateUnbounded` 一樣，只是排隊的地方換成你看不到的地方。
> 所以我們換成 `select` 加 `default`。意思是：能放進去，就放；放不進去，不要等，直接走 `default`。`default` 裡，我們把剛才預扣的那一個還回去，回 `ErrBusy`，handler 把它變成 503，加一個 `Retry-After: 1`。
> C# 的朋友，這一整段就是 `channel.Writer.TryWrite(job)`，回傳 false 的時候你自己決定怎麼辦。Java 的朋友，是 `queue.offer(job)`，不是 `queue.put(job)`。一個字母的差別，是「排隊」和「背壓」的差別。
> 這是整集最重要的一行。**背壓不是「排得更有效率」，是「滿了就說不」。**

> 當然，說「不」的人，感覺不太好。可是你想想：一個被擋在門外的人，兩秒之後知道要重試；一個放進佇列的人，三分鐘之後才知道失敗。哪一個比較像在服務客人？
> 我們現在的結帳頁，終於學會了客服最難的一句話：「現在人比較多，請您等一下再過來。」它只是說得比客服快。

【畫面】程式裡還有一個細節：客人在排隊的時候關掉分頁。

> 還有一個細節：排隊的人如果自己走了，怎麼辦？它的預扣不能一直占著。我們讓每個排隊的工作有一個「認領」的旗標，用一個 `CompareAndSwap`：worker 先認領就是 worker 的，客人先放棄就是客人的。誰贏了，誰負責把預扣還回去，只還一次。worker 之後看到那張被放棄的單，直接跳過，不浪費一次資料庫呼叫。

## 8:20 第三段：進資料庫的只有幾個 worker

【畫面】`FlashSale.Run`；`postgres.OpenWithMaxConns`；`cmd/api/main.go` 的 `DB_MAX_CONNS`。

> 最後一塊：誰從 channel 裡拿工作？四個 worker goroutine，一個迴圈，從 channel 讀，下一張單，回結果。同一個時間，最多四個在資料庫裡。
> 連線池也要有上限：`OpenWithMaxConns`，預設十。PostgreSQL 預設的 `max_connections` 是一百，每個 API 實例最多佔十個，十個實例就用完。**這個上限是我們對資料庫的承諾。** 要多的連線，請排隊，不是再開。
> worker 的數字刻意比連線池小：連線池除了搶購，還要給前面第 8、第 9 集的寄信 worker、清潔工，還有每一個沒在搶購的人。這幾個數字加起來，就是商店的總容量：四個在資料庫裡，六十四個在排隊，第六十九個，不好意思，請等一下再過來。

> 我們給整間店設了一個容量。**它第一次，不是由「撐到哪裡算哪裡」決定的。** 以前的容量是：當機的那一刻。

> 最後還是要說：啟動的方式，跟第 8、第 9 集一樣，誰啟動誰停。`main.go` 裡那個 `workerCtx` 現在管三個 goroutine，同一個 `defer` 取消，再等三個都結束，才輪到 `pool.Close`。

## 10:00 證明：三件事

【畫面】`go test ./internal/service -run Flash -v`，然後 `go test -tags=integration ./internal/service -run Integration -v`，全綠。

> 第一件，預扣不超賣。五台顯示器，一百個人同一瞬間來搶。結果：剛好五張訂單、九十五個「賣完了」，資料庫庫存停在零，不是負的；而且資料庫只看到五次下單呼叫，不是一百次。計數器擋掉了其餘的九十五個。
> 第二件，channel 滿了會拒絕。單元測試裡，一個 worker、一個排隊位置：第一個人在資料庫裡，第二個人在排隊，第三個人進來，**當場**被回 `ErrBusy`，資料庫的呼叫次數還是一次，預扣的那一個也還回去了。整合測試再用真的資料庫跑：兩個 worker、排隊五個、兩百個人同時來。有人被拒絕；成交加被拒絕剛好是兩百；而且 Redis 計數器等於庫存減去訂單數，被拒絕的人，一個都沒讓庫存少掉。
> 第三件，資料庫連線數有上限。連線池設成四個、worker 三個，一百五十個人同時買。我們每一毫秒去量連線池：忙碌的連線，最多三個，總連線數沒有超過四個。

> 順便說，這個測試如果量的是「請求數」，會很漂亮；我們量的是連線池的 `AcquiredConns`，因為連線池才是資料庫真正感覺到的東西。

> 現在是雙 11 晚上 10 點 31 分。老闆問：「剛剛是不是有很多人看到『忙碌中』？」
> 我說：「對。比起讓他們看到轉圈圈，我們選擇讓他們看到一句誠實的話。」
> 他沉默了一下，說：「那句話下次可以寫得親切一點。」
> 這是這個晚上，第一個我們沒辦法用程式修的需求。

## 附錄 B：待確認

- 笑點時間點是估的，錄製前對照實際口播長度重排。
- Redis 計數器和資料庫的庫存會各自偏離：第 9 集清潔工把逾時訂單的庫存還給資料庫，但不會還給 Redis 計數器。所以搶購期間，計數器只會比真相少，不會多：寧可少賣，不會超賣。這個偏差本集不處理，也沒有測試。
- 預扣之後、下單之前如果程序被砍掉，那一個預扣不會還回去（沒有 TTL，也沒有對帳）。同樣是少賣，不是超賣。
- 搶購用 `SET NX` 開賣，重啟不會把計數器重設成滿的；如果 Redis 被清掉，搶購路由會回 500（`ErrSaleNotOpen`），不會自動重開。
- 沒有帳號，所以「一人限購」做不到：同一個人可以把十台全買走。本集不處理。
- 搶購路由不在 OpenAPI 合約裡（跟綠界回呼一樣是單獨的 chi 路由）；經過第 4 集的每 IP 限流，所以一個 IP 做壓測要調 `RATE_LIMIT_RPS`、`RATE_LIMIT_BURST`。
- `Retry-After` 固定回 1 秒；沒有依佇列長度調整。
- 排隊沒有自己的逾時，只靠客人的連線（`ctx`）；`ErrBusy` 的另一個來源是 `Run` 已停止，這個情境的完整關機流程是第 12 集。
- 預設值：worker 4、排隊 64、`DB_MAX_CONNS` 10；用 `FLASH_SALE_PRODUCT_ID`、`FLASH_SALE_STOCK`、`FLASH_SALE_WORKERS`、`FLASH_SALE_QUEUE`、`DB_MAX_CONNS` 調整。沒設 `FLASH_SALE_PRODUCT_ID` 就沒有這條路由。
