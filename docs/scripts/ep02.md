## 1:30 C# 會怎麼寫（為什麼在 Go 行不通）

【畫面】左邊 Visual Studio：`AppDbContext : DbContext`、`DbSet<Product> Products`，Package Manager Console 打 `Add-Migration Init`、`Update-Database`。

> 如果是 C# 的朋友，這個早上你會這樣過：
> 寫一個 `Product` 類別，寫一個 `AppDbContext`，裡面放 `DbSet<Product>`。
> `Add-Migration`，`Update-Database`，表就建好了。查詢呢？`await db.Products.OrderBy(p => p.Id).ToListAsync()`。
> 一行 SQL 都沒寫，資料就出來了。是不是很美？

> 當然，EF Core 是很強的工具，我自己也用了很多年。可是它有個習慣：**SQL 是它幫你寫的**。
> 平常沒事。出事的時候，你打開 log，看到一段你從來沒寫過的 SQL：七個 `LEFT JOIN`，一個子查詢，還有一堆 `[s0]`、`[t1]` 這種別名。
> 你問它：「這是誰寫的？」它說：「是你寫的 LINQ。」你說：「我只寫了 `.Include()`。」
> 好，這段對話我們就停在這裡，再講下去就是 N+1 查詢的家族聚會了。

> Java 的朋友一樣：JPA、Hibernate、`@Entity`、`@OneToMany(fetch = LAZY)`。同一個故事，換了一個註解。

【畫面】Go 的套件搜尋頁，搜 ORM，跳出好幾個結果；畫面上打一個大問號。

> 那 Go 呢？Go 有 ORM 嗎？有，社群裡有好幾個。
> 可是 Go 社群有個很明顯的傾向：**SQL 自己寫**。理由很簡單：SQL 本來就是一個好語言，我們幹嘛把它翻譯成另一種語言，再請工具翻譯回來？
> 那 SQL 自己寫，不就回到手寫 `reader["price"]` 然後轉型的年代了嗎？
> 這說明什麼？說明我們需要一個工具：**我們寫 SQL，它寫 Go**。好那我們來看。

## 3:30 第一段：goose migration（表是怎麼長出來的）

【畫面】`docker-compose.yml`，再切 `docker compose up -d --wait`，綠色的 Healthy。

> 好那我們先有一個資料庫。`docker compose up`，一個 PostgreSQL 就起來了。
> 這裡的帳號密碼是 `goshop`、`goshop`。我先講清楚：這是本機用的拋棄式預設值，不是密鑰。真的密碼不會出現在 repo 裡，這件事之後上雲的時候再講。

【畫面】`db/migrations/00001_create_products.sql`。

```sql
-- +goose Up
CREATE TABLE products (
    id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name       text        NOT NULL,
    price_twd  integer     NOT NULL CHECK (price_twd >= 0),
    created_at timestamptz NOT NULL DEFAULT now()
);

-- +goose Down
DROP TABLE products;
```

> 這是一個 migration。它就是一個 SQL 檔，上半部是「往前」，下半部是「退回」。
> EF Core 的 migration 是 C# 程式碼，它會幫你從類別推出 SQL；goose 反過來，你直接寫 SQL，它只負責記住「哪幾個檔跑過了」。
> 注意 `price_twd` 上面那個 `CHECK`。價格不能是負的。這個規則寫在資料庫裡，不管是哪個程式、哪個實習生、哪一支半夜的修正腳本，都過不了這一關。

> 第二個檔是種子資料，就是第 1 集那三件商品：機械式鍵盤、人體工學滑鼠、27 吋螢幕。
> 它們從記憶體搬家到資料庫，戶籍正式遷入。

【畫面】`db/migrations.go`，圈出 `//go:embed migrations/*.sql`。

> 那 migration 誰來跑？我們讓 API 啟動時自己跑。
> 看這行 `//go:embed`。它把整個 migrations 資料夾**編進執行檔裡**。部署的時候你不用另外帶 SQL 檔，一個二進位檔走天下。
> 對 C# 的朋友來說，這有點像把檔案設成 Embedded Resource，只是不用去專案檔裡勾選，一行註解就搞定。

## 5:30 第二段：sqlc（我們寫 SQL，它寫 Go）

【畫面】`db/queries/products.sql`。

```sql
-- name: ListProducts :many
SELECT id, name, price_twd
FROM products
ORDER BY id;
```

> 好，重頭戲。這是一支查詢。上面那行註解是給 sqlc 看的：這支查詢叫 `ListProducts`，會回傳很多列。
> 然後我們跑 `make sqlc`。

【畫面】終端機跑 `make sqlc`，左側檔案樹長出 `internal/repository/dbgen/`；切到 `products.sql.go`。

> sqlc 讀了我們的 migration，知道 `products` 表長什麼樣；再讀這支查詢，知道要拿哪幾欄。然後它產生了這個：

```go
type ListProductsRow struct {
    ID       int32
    Name     string
    PriceTwd int32
}

func (q *Queries) ListProducts(ctx context.Context) ([]ListProductsRow, error)
```

> 一個型別、一個函式，全部是**編譯期**就確定的。
> 我故意把 SQL 裡的 `price_twd` 打錯成 `price` 再跑一次——

【畫面】`make sqlc` 噴紅字：`column "price" does not exist`。

> 紅字。不是上線後在 log 裡看到，是在我按下產生的那一秒。
> EF Core 的朋友可能會說：LINQ 也是編譯期檢查啊？對，可是 LINQ 檢查的是你的 C# 類別，不是你的資料庫。類別跟資料表對不上的時候，它會非常有禮貌地等到執行期才告訴你。
> sqlc 檢查的是 SQL 對 schema。我比較喜歡這種沒禮貌的。

> 我們有一個 SQL 檔，產生出一個 Go 檔。這兩個要一起進 git 嗎？要。產生的程式碼也是程式碼，code review 的人要看得到它長什麼樣。

【畫面】`internal/repository/product.go`。

> 產生的碼我們不直接給 service 用，外面包一層薄薄的 repository：

```go
func (r *Products) List(ctx context.Context) ([]Product, error) {
    rows, err := r.q.ListProducts(ctx)
    ...
    out = append(out, Product{ID: int(row.ID), Name: row.Name, PriceTWD: int(row.PriceTwd)})

```

> 它只做一件事：把資料庫的型別翻成我們自己的 `Product`。為什麼要多這一層？因為 sqlc 產生的型別名字是跟著 SQL 走的，我們不想讓 `ListProductsRow` 這種名字一路漏到 handler。

> 好，驗收時間。第 1 集我說 service 一個字都不用改——

【畫面】`git diff ep01 -- internal/service/product.go`，畫面一片空白。

> 空的。`ProductStore` interface 還是那一行 `List(ctx)`。舊的記憶體版有這個方法，新的資料庫版也有，方法對上就滿足。

## 8:00 第三段：pgx 連線池與 `context.Context`

【畫面】`internal/platform/postgres/postgres.go`。

> 最後一塊：連線。我們用 pgx，它是 Go 裡功能最完整的 PostgreSQL driver。
> `pgxpool.New` 給你一個連線池。對 C# 的朋友來說，這就是 ADO.NET 的 connection pool，差別是：C# 的池藏在 connection string 後面，你看不到它；Go 的池是一個你拿在手上的物件，`*pgxpool.Pool`。

```go
pool, err := pgxpool.New(ctx, url)
...
if err := pool.Ping(ctx); err != nil {
```

> 建完我們馬上 `Ping` 一次。為什麼？因為 `DATABASE_URL` 打錯的時候，我希望 API **啟動就死**，而不是活得好好的，等第一個客人進來才死。
> 啟動就死是一種美德。它死在部署的時候，旁邊有人；它死在第一個請求的時候，旁邊只有客人。

> 注意到了嗎？每個函式的第一個參數都是 `ctx context.Context`。`Open(ctx, url)`、`List(ctx)`、`ListProducts(ctx)`，一路往下傳。
> C# 的朋友會想到 `CancellationToken`。很像，而且在 C# 裡它通常是最後一個參數、還常常是選填的，所以大家常常忘了傳。
> Go 的慣例是：**會碰 I/O 的函式，第一個參數就是 ctx**。放第一個，就很難假裝沒看到。
> 那 ctx 到底能幹嘛？今天我們只用到一件事：使用者把請求取消了，查詢也跟著取消。它還能帶逾時、帶值，那是第 9 集的事，今天先讓它乖乖排第一個。

【畫面】`cmd/api/main.go`。

```go
pool, err := postgres.Open(ctx, dbURL)
if err != nil {
    return err
}
defer pool.Close()

repo := repository.NewProducts(pool)
svc  := service.NewProductService(repo)
h    := handler.New(svc, logger)
```

> 回到 `main`。接線還是那三行，只是第一行從「new 一個記憶體」變成「把連線池交給 repository」。
> 然後是 `defer pool.Close()`：函式結束的時候，把池子關掉。
> 這裡有一個陷阱。原本的 `main` 出錯會呼叫 `os.Exit(1)`。`os.Exit` 是直接拔插頭，**defer 不會跑**。
> 所以我們把所有事情搬進一個 `run()` 函式，它只回傳 error，由 `main` 決定要不要退出。這樣 Ctrl+C 的時候，`run` 正常 return，`defer` 正常執行，池子正常關。
> 你可能會問：那正在處理中的請求呢？好問題，把那個問題寄放在第 12 集，那集整集都在講它。

## 11:30 三點收尾

> 好，我們收一下。
> **第一**，Go 不靠 ORM。我們寫 SQL，sqlc 讀 schema 和查詢，產生型別安全的 Go 碼；寫錯欄位，產生的那一秒就紅字。
> **第二**，schema 用 goose migration 管，SQL 檔用 `go:embed` 編進執行檔；連線池是 `*pgxpool.Pool`，在 `main` 建、在 `main` 用 `defer` 關，所以 `main` 不直接 `os.Exit`。
> **第三**，會碰 I/O 的函式第一個參數是 `ctx context.Context`；而因為 interface 定義在使用端，換掉整個資料層，service 一個字都沒改。
