## 1:40 C# 會怎麼寫（為什麼在 Go 行不通）

【畫面】左邊 Visual Studio：`using var tx = new TransactionScope();`、`db.Database.BeginTransaction()`、`FromSqlRaw("... WITH (UPDLOCK)")`。右邊是空的 `orders.go`。

> C# 的朋友，這個晚上你大概這樣做：
> 開一個 `TransactionScope`，或是 `BeginTransaction`，查庫存的時候加 `UPDLOCK` 或 `FOR UPDATE`，最後 `Complete` 或 `Commit`。Java 的朋友更省事：在 service 方法上貼一個 `@Transactional`，再給 repository 查詢加 `@Lock(PESSIMISTIC_WRITE)`。Spring 會在你的方法前後，幫你 begin、commit，丟例外就 rollback。
> 注意你**沒寫**什麼：`Begin`、`Commit`、`Rollback`。有個代理（proxy）在你看不見的地方，替你包好了。

> 當然，這很方便。可是它把這次事故最關鍵的東西藏起來了：**交易從哪裡開始、到哪裡結束**。不小心把庫存檢查放在註解的範圍外面，你就蓋出一台非常有禮貌的超賣機器。你上次讀自己的代理堆疊追蹤，是什麼時候？

> Go 沒有註解，沒有代理，沒有 scope 物件。所以交易的邊界，是三行你看得見的程式。來看。

【畫面】`internal/repository/orders_integration_test.go`，`naiveOrders.Place`。

> 讀跟寫中間那段暫停，只是讓競爭從「很可能」變成「一定」。bug 在程式的形狀，不在那段暫停。

## 5:30 第二段：修法，是三行看得見的程式

【畫面】`internal/repository/orders.go` 的 `Place`，圈出 `Begin`、`defer`、`Commit`。

```go
tx, err := r.db.Begin(ctx)
if err != nil { ... }
defer func() { _ = tx.Rollback(ctx) }()
// ... 鎖、檢查、扣庫存、寫訂單 ...
return order, tx.Commit(ctx)
```

> 整個交易就這樣。`Begin`。馬上接一個 `defer tx.Rollback`。然後做事。最後 `Commit`。
> 關鍵是那個延後執行的 rollback。中間任何一行回傳錯誤，函式離開，延後的 rollback 就把一切復原。走到 `Commit` 的話，交易已經結束，rollback 變成無害的空動作。一個模式，沒有 try/catch，沒有 `finally`。
> Java 的朋友：這就是你只在最上面寫一次、而且不會忘記的 `try`/`finally`，因為 `defer` 在每一條離開路徑都會執行。

【畫面】`db/queries/products.sql` 的 `LockProduct`，圈出 `FOR UPDATE`。

> 再來是鎖。`SELECT id, price_twd, stock FROM products WHERE id = $1 FOR UPDATE`。最後那幾個字就是整個修法。
> 它把那一列鎖到交易結束。第二個買家走到這一行，就在這裡等。第一個提交之後，庫存是零，第二個拿到鎖、讀到零，得到「缺貨」。檢查跟寫入，變成一個不可分割的動作。
> 當然，單一商品你也可以寫 `UPDATE ... SET stock = stock - 1 WHERE stock >= 1`，不用鎖，老實說這對單列是很好的答案。可是一張訂單有很多行、有規則、還要同時讀價錢。有了鎖，我們就能用一般的 Go 程式讀、判斷、寫。

【畫面】對 lines 做 `sort.Slice`。

> 還有一個細節。上鎖前，我們先把商品行按 id 排序。兩張訂單用相反的順序要同樣兩樣商品，各自握著一把鎖、等對方放手，那就是死結。排好序，它們就乖乖排隊。這一點有測試。

## 8:30 第三段：全有或全無，還有規則放哪裡

【畫面】`TestOrders_FailedOrderRollsBackEverything`。

> 交易的另一半是「全無」。測試：一張兩行的訂單。第一行，鍵盤兩個，沒問題。第二行，螢幕兩台，不夠。我們預期得到錯誤，而且預期鍵盤放回架上。
> 之前庫存十個。接著再下一張買一個鍵盤的訂單，立刻成功，剩九個：失敗的那張一個都沒拿走，也沒留下鎖。延後的 rollback 做完它的工作。

【畫面】`service.OrderStore` 與 `repository.Orders`；`service.CheckoutCart` 與 `repository.Carts`。

> 再說介面。訂單 service 宣告自己需要什麼：`OrderStore`，只有一個方法 `Place`；還有 `CheckoutCart`，兩個方法，讀購物車、從裡面移除。`repository.Orders`，和上一集的 Redis `Carts`，都沒被告知就滿足了它們。測試裡的天真版本也滿足 `OrderStore`，所以我們才能把 bug 換進去重演。隱式介面，在做它的工作。
> service 把錯誤換成自己的：缺貨、商品不見。handler 再把它們變成 `409` 跟 `404`。那個含著 IP 位址的資料庫錯誤呢？維持是一個普通的 `500`，客人看不到。

## 11:45 三點收尾

> 好，我們收一下。
> **第一**，在 Go，交易就是 `Begin`、`defer tx.Rollback`、`Commit`。沒有註解，沒有代理。邊界就在畫面上，你讀得到。
> **第二**，「先檢查再寫」就是競爭，除非中間有東西握著鎖。`SELECT ... FOR UPDATE` 把鎖握到交易結束。鎖定要依固定順序，交易要短。
> **第三**，修之前先重現。一個隨時能超賣的測試，比一個你自己相信的修法有價值。
