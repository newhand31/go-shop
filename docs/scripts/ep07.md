# 第 7 集｜付兩次錢（口播稿草稿 v0）

- 目標長度：12–13 分鐘（約 3,500 字口播）
- 本集唯一主概念：**冪等鍵**：綠界會重送回呼，所以「同一筆付款只入帳一次」要由資料庫的唯一鍵（`UNIQUE` + `ON CONFLICT DO NOTHING`）來保證；驗章（`crypto/sha256`、`net/url`）是前置條件，自己寫、只用標準庫
- 程式對應：tag `ep07`（`git checkout ep07`）
- 風格依 [style-guide.md](../style-guide.md)；【畫面】是剪輯提示，不唸出來。

> 這是一個非常守規矩的系統：**每一個通知，我們都認真對待。** 認真到，同一個通知，我們認真對待了兩次。

## 1:40 C# 會怎麼寫（為什麼在 Go 行不通）

【畫面】左邊 ASP.NET Core 的 controller：`[HttpPost("ecpay/callback")]`，`if (!await db.Payments.AnyAsync(p => p.TradeNo == tradeNo)) { db.Payments.Add(...); await db.SaveChangesAsync(); }`。右邊是空的 `payments.go`。

> C# 的朋友，你大概會這樣寫：收到回呼，先查「這個交易編號有沒有記過」，沒有就新增、`SaveChanges`。Java 的朋友換成 `existsByTradeNo`，再 `save`。看起來很合理。
> 我們來看這兩行中間發生什麼事。綠界在 0.2 秒內重送了第二次，兩個請求各自跑到 `AnyAsync`，**各自**看到「沒記過」，**各自**新增。先查再寫，中間沒有任何東西擋著。這個結構你在第 6 集看過了，它有名字：競爭。
> 當然，你可以在 Controller 上貼一個去重的 Filter，或是接一個冪等的套件。可是 ASP.NET Core 和 Spring 都沒有內建「這個請求只處理一次」；那個 Filter 還是得有人寫、有人存狀態、有人想到要處理兩個請求同時進來。我們沒有 middleware 魔法可以指望。

> Go 一樣沒有。所以這一集的主角不是程式，是資料庫的一行宣告。

## 3:30 第一段：先確認是綠界打來的（自己寫驗章）

【畫面】`internal/payment/ecpay/ecpay.go`，`CheckMacValue`。

> 在去重之前，先問一個更基本的問題：**這通電話，真的是綠界打的嗎？** 回呼是一個公開的網址，任何人都能對它送一份「訂單四十二號已付款」。
> 綠界的做法是簽章，叫 `CheckMacValue`。規則寫在文件裡，我們照著寫，全部只用標準庫。六步：
> 一，欄位依名稱排序，不分大小寫。二，串成 `k=v&k=v`，前面加 `HashKey=`、後面加 `HashIV=`。三，整串做 URL encode。四，全部轉小寫。五，把 `!`、`*`、`(`、`)` 還原，因為 .NET 的 encode 不動它們，Go 的會動。六，SHA-256，轉大寫十六進位。
> 第三步到第五步是這一集最容易踩的坑：少還原一個括號，簽章就整個對不起來，而且錯誤訊息只會告訴你「不一致」。

【畫面】`ecpay_test.go` 的 `TestCheckMacValue_GoldenVectors`。

> 我們怎麼知道自己寫對了？這個測試的預期值，是另一個程式用另一種語言、照同樣六步算出來的。它含空白、括號、星號、單引號，還有大小寫混合的欄位名稱，主要容易寫錯的規則都在裡面（`~` 和中文品名還沒有，錄影前補）。拿自己的輸出對自己的輸出，那叫自我感覺良好，不叫測試。

【畫面】`Verify`，圈出 `subtle.ConstantTimeCompare`。

> 兩個細節。第一，先驗章，才讀欄位：沒簽章的內容，就是攻擊者輸入。第二，比對簽章用 `ConstantTimeCompare`，回應時間不會洩漏「前面幾個字元猜對了」。
> 測試把每一種作法都試一遍：金額在簽章後被改掉、訂單編號改一位、多塞一個欄位、簽章缺席、簽章是亂碼、用別把 key 簽。全部是 `ErrBadSignature`。

## 5:45 第二段：冪等鍵是一行資料庫宣告

【畫面】`db/migrations/00004_add_payments.sql`，圈出 `trade_no text NOT NULL UNIQUE`。

> 驗章通過，才輪到今天的事故。
> 綠界給每一筆付款一個交易編號，`TradeNo`。重送的回呼，編號一模一樣。這就是冪等鍵：**同一件事，永遠帶同一個名字。** 我們把它存進 `payments` 表，並且宣告 `UNIQUE`。
> 注意我們沒有寫「先查有沒有」。我們把「只能有一筆」交給資料庫去保證。兩個請求同時進來，資料庫讓其中一個先寫，另一個會發現撞到了。

【畫面】`db/queries/payments.sql`：`ON CONFLICT (trade_no) DO NOTHING`。

> 撞到的時候怎麼辦？如果直接回錯誤，綠界會當作我們沒收到，繼續重送，我們就陷入一個自己製造的迴圈。所以用 `ON CONFLICT DO NOTHING`：撞到不是錯誤，只是「影響 0 列」。

【畫面】`internal/repository/payments.go`，`Record`。

```go
n, err := q.InsertPayment(ctx, ...)
// ...
case n == 0:
    return false, nil // already recorded; the first call did the work
```

> `Record` 的回傳值是「這次有沒有真的記到」。零列，就是「這筆已經記過了」，回 `false`、不是錯誤。service 把它變成一行日誌：「重複的回呼，忽略」。對綠界來說，第一次和第十次，答案都是 `1|OK`。
> 第 6 集學的交易在這裡又用上了：記付款和把訂單標成已付，在同一個交易裡。金額對不上的話，整個交易回滾，連付款那一列也不留。

## 8:20 第三段：兩種「失敗」，要分開回

【畫面】`internal/handler/payment.go`，`ECPayCallback` 的 `switch`。

> 最後是回應的細節。綠界只認一個字串：`1|OK`。收到別的，它就重送。這一點我們要拿來用。
> 簽章不對、金額不對、找不到訂單：這些重送也不會變好，回 400（綠界還是會照規則重送幾次，但每次結果都一樣，所以我們在日誌留一條就夠）。我們自己的問題，比如資料庫掛了：回 500，**不要**回 `1|OK`。因為我們沒記到，要綠界再試一次。回 `1|OK` 的意思是「我收下了」，不是「我看到了」。
> 還有一個：付款失敗的通知，我們也回 `1|OK`，只記日誌。重送它，結果不會變。

【畫面】`WithPaymentCallback`，路由圖：外層 router，接著是 `/payments/ecpay/callback`，其餘交給原本的 API。

> 這個路由掛在限流和 session 外面。打電話來的是綠界的伺服器，不是訪客；它沒有 cookie，也不該被當成「一秒打一千次的 IP」擋掉。它的身分證明就是簽章。

## 10:00 證明：同一筆回呼，同時送十次

【畫面】`go test -tags=integration ./internal/repository -run Payments -v` 全綠。

> 先看測試。同一份簽好章的回呼，十個 goroutine 等同一個信號，同時送出。結果：十個都拿到 `1|OK`，`payments` 表一列，訂單已付款。
> 接著兩個反例：不同的 `TradeNo` 是兩筆不同的付款，會記兩列，只有重複的才被丟掉。偽造的簽章、金額不符、不存在的訂單，全部 400，而且資料庫裡什麼都沒留下。
> 還有一個：我們繞過 service，直接對資料庫塞兩次一樣的 `TradeNo`，第二次會被資料庫自己拒絕。冪等鍵不靠我們的程式有多乖。

> 我還做了一件事：把 `ON CONFLICT` 那一行刪掉，再跑一次。測試變紅，十次裡有人拿到 500。測試會因為修法被拿掉而失敗，我們才有資格說它在保護什麼。

> 現在是晚上 9 點 55 分。財務傳來：「四十二號，一筆。對得上。」
> 我說：「它本來就該只有一筆。」

## 11:45 三點收尾

> 好，我們收一下。
> **第一**，回呼公開在網路上，先驗章再讀欄位。自己寫只要六步，但要拿另一個實作算出來的值當預期值。
> **第二**，沒有人幫你去重。冪等鍵自己存，存在資料庫，用 `UNIQUE` 加 `ON CONFLICT DO NOTHING`，不要「先查再寫」。
> **第三**，回應要分清楚：你的錯，不回 `1|OK`；重複的，回 `1|OK`。
>
> 老闆的下一則訊息：「客人付了錢，說他沒收到任何通知。」

## 附錄 B：待確認

- 啟動需要 `ECPAY_*` 三個環境變數；示範用 `ECPAY_SANDBOX=1`。沒設就拒絕啟動，避免用公開金鑰驗章的端點被偽造。
- 沒有「建立付款」的程式：本集只做回呼端，用綠界公開的 sandbox 帳密與 `Sign` 輔助函式在測試裡扮演綠界。真的導向綠界結帳頁留給後續，錄影不要暗示已經能收錢。
- `MerchantTradeNo` 用 `GS` 加訂單編號（綠界上限 20 個英數字）；實務上同一張訂單重新付款需要新的編號，這裡沒有處理。
- 一張訂單收到兩筆不同 `TradeNo` 的付款（真的付了兩次）會各記一列，訂單維持已付款。退款與人工對帳不在本集範圍。
- `paid_at` 用 `COALESCE`，重複標記不會改掉第一次的時間。
- 預期值向量是用另一個語言的獨立實作算出來的，不是從綠界官方文件抄的範例；錄影前可再用官方 sandbox 實際打一次確認。
- 道別固定句尚未定案（沿用前幾集占位）。
- 結帳（`POST /checkout`）本身仍不冪等，這一集沒有碰它。
