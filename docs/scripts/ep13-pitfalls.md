## 1:40 C#／Java 會怎麼想（為什麼在 Go 會騙到你）

【畫面】左邊 C#：`string? s = null; if (s == null)`。中間 C#：`foreach (var x in list) tasks.Add(() => x);`。右邊 `var head = list.GetRange(0, 2); head.Add(99);`。

> 先講我們的直覺。C# 的 `null` 就是一個值，`x == null` 問的是「這個東西是空的嗎」，一個問題一個答案。
> `foreach` 的變數，C# 5 之後每一圈都是新的一份，你在 closure 裡抓它，不會出事。
> `List<T>.GetRange` 給你的是複製品，你對它 `Add`，原本的 list 動都不動。
> **三個直覺在 C# 全都對，在 Go 全都有例外。** 所以不是你笨，是你太會 C# 了。

## 2:30 第一個坑：nil interface 不等於 nil

【畫面】程式碼 `internal/pitfalls/nilerror.go`。

> 先看這個函式：

```go
func findBuggy(id int) error {
	var err *NotFoundError
	if id != 1 {
		err = &NotFoundError{ProductID: id}
	}
	return err
}
```

> 找得到商品的時候，`err` 還是 nil 指標，我們把它回傳了。呼叫的人寫 `if err != nil`，結果是 **true**。
> 為什麼？因為 Go 的 interface 是一個「兩格的盒子」：第一格放型別，第二格放指標。
> 我們放進去的是：型別 `*NotFoundError`，指標 nil。**盒子裡有東西，只是東西是空的。** 真正的 nil interface 是兩格都空。
> **這就像拿一個空的便當盒去問「有沒有便當」，盒子在，便當不在，可是你問的是盒子。**
> 修法很無聊：沒有錯誤就老實回 `return nil`。

```go
func findFixed(id int) error {
	if id != 1 {
		return &NotFoundError{ProductID: id}
	}
	return nil
}
```

> 規則只有一條：**回傳 `error` 的函式，成功的路徑一定寫 `return nil`，不要回傳一個具體型別的變數。** 具體型別的指標變數一旦當成 interface 回傳，就多了一格型別。
> 這個坑最常出現在自訂的錯誤型別。你寫一個 `validate()`，回傳 `*ValidationError`；沒問題的時候，你順手把那個變數回傳了。外面用 `error` 接，就中了。
> 懷疑的時候，用 `%T` 和 `%v` 各印一次。`%T` 說 `*pitfalls.NotFoundError`，`%v` 卻說 `<nil>`。**型別有、值是 nil，就是這個坑的指紋。**
> C# 的朋友，你可以把它想成：C# 沒有這個問題，因為 `null` 只有一種。Go 有兩種，「空盒子」和「沒有盒子」。

## 4:30 第二個坑：迴圈變數捕捉（Go 1.22 前後）

【畫面】程式碼 `loopvar_new.go` 與 `loopvar_old.go` 並排。

> 兩個檔案，一模一樣的迴圈：

```go
for i := 0; i < n; i++ {
	fns = append(fns, func() int { return i })
}
```

> 跑三圈，每一圈把一個 closure 放進清單，之後呼叫它們。你覺得印出什麼？
> 在 Go 1.22 之後：0、1、2。在 1.21 以前：**3、3、3。**
> 舊版的規則是，整個迴圈只有一個 `i`，三個 closure 抓的是同一個。迴圈結束時 `i` 是 3，大家一起說 3。
> **我當年的第一個 goroutine 迴圈就是這樣：開了十個工人，十個都在處理最後一筆訂單。公司給了我十倍的訂單量，只有一筆是真的。**
> 1.22 之後語言改了：每一圈有自己的 `i`。這個 repo 的 `go.mod` 寫 Go 1.27，所以你預設是安全的。
> 更常見的版本是 goroutine：`for _, o := range orders { go process(o) }`。1.22 以前，十個 goroutine 常常都拿到最後一筆。當年的護身符是在迴圈裡寫 `o := o`，或把 `o` 當參數傳進去。
> 還有一個容易漏掉的細節：新規則看的是 `go.mod` 裡那一行 `go 1.22`（或更新）。你把工具鏈升到 1.27、卻沒改 `go.mod`，行為不會變。**升級編譯器不等於升級語言版本。**
> 那為什麼我們還要講？因為兩個原因。第一，你會讀到舊程式碼，裡面會有 `i := i` 這種怪行，那是當年的護身符。第二，**語言版本是看每個檔案的**：`go.mod` 的版本是預設，檔案開頭的 `//go:build go1.21` 可以把這一個檔案降回舊規則。我們就是用這招，在同一個 repo 裡讓兩種行為並排。

> 好那我們來看，這在 C# 是什麼：C# 5 把 `foreach` 改成每圈一個新變數，早就走過同一條路。注意是 `foreach`；C# 的 `for` 三段式迴圈到今天仍然共用一個變數。Go 1.22 改的是 `for`。

## 6:30 第三個坑：slice 共用底層陣列

【畫面】程式碼 `slices.go`，下面畫四格方塊：10、20、30、40，上面蓋一個「視窗」框住前兩格。

> 最後一個。購物車有四件商品，我們要取前兩件，再加一件：

```go
func firstBuggy(cart []int, n, extra int) []int {
	head := cart[:n]
	return append(head, extra)
}
```

> 結果回傳 10、20、99。看起來正常。可是購物車變成了 **10、20、99、40**：第三件商品被改掉了。
> 原因是 slice 不是陣列，是一個「視窗」：三個欄位，指標、長度、容量。`cart[:2]` 是同一塊陣列上的另一個視窗，長度 2，**容量還有 4**。`append` 看到還有空間，就直接寫進去。
> **這就像你借同事的螢幕看兩行，結果你在第三行打字，他的檔案就改了。**
> 修法是把視窗的容量也鎖住：

```go
head := cart[:n:n]
```

> 第三個數字是容量上限。現在 `append` 發現沒有空間，會配一塊新的陣列、把資料複製過去，原本的購物車安全。或者用 `slices.Clone`，更直白。
> 更陰險的版本是：你自己沒有 `append`，你把 `head` 交給別的函式，那個函式 `append` 了。你完全不知道，因為函式簽名看不出它會不會寫進去。
> 所以公開函式回傳子 slice 之前，先想一下要不要 `slices.Clone`。反過來，如果只是讀，就不用複製：視窗之所以便宜，就是因為它不複製。**便宜的代價，是你要知道誰擁有這塊記憶體。**
> 反問一下：為什麼這個坑在 C# 不存在？因為 `GetRange` 給你複製品。Go 的 `cart[:n]` 給你的是同一塊記憶體的另一扇窗，**複製要自己說**。

## 8:15 怎麼提前抓到這三顆

> 我們來整理一下，這三顆在 code review 抓得到嗎？
> 第一顆，`go vet` 不會抓（我們跑過，乾淨過關）；額外的 linter 能抓到部分情況，但沒有人保證。**最可靠的防線不是工具，是那條規則：成功就寫 `return nil`。**
> 第二顆，升到 1.22 就解決了。`go vet` 的 `loopclosure` 也會在 goroutine 與 `defer` 的情況提醒你。
> 第三顆，沒有工具。你只能記得：**`append` 前先問一句，這個 slice 的容量是誰的？**
> 當然，你也可以不記，用測試記。
> 還有一個 review 習慣：看到 `append` 的第一個參數不是自己剛建立的 slice，就多問一句「這是誰的？」。這句話五秒，比事故後的追查便宜。

## 10:45 三點收尾

> 第一，interface 是兩格盒子：型別加指標。回傳 `error` 的時候，沒事就寫 `return nil`。
> 第二，Go 1.22 起每一圈有自己的迴圈變數，而且語言版本是看檔案的；讀舊程式碼時，`i := i` 是歷史，不是迷信。
> 第三，slice 是視窗不是複製品；`append` 之前問容量是誰的，需要隔離就用 `[:n:n]` 或 `slices.Clone`。
> 這三個都不是 Go 的缺陷，是 Go 把「便宜」放在「保險」前面。你要的保險，自己買。
> **我們解決了三顆地雷，順便證明了：最危險的 bug，是編譯器覺得沒問題的那種。**
> 那今天就到這裡。我們下一個系列見。
