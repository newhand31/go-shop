## 1:40 C#／Java 會怎麼寫（為什麼在 Go 行不通）

【畫面】左邊 Spring Boot：加 Micrometer Tracing 和 Actuator，`/actuator/prometheus` 自動出現，log 的 MDC 自動多一個 `traceId`；C# 版：Application Insights 一行 `AddApplicationInsightsTelemetry()`，`ILogger` 自動帶 `TraceId`。右邊是空的 `main.go`。

> Java 的朋友，你加幾個 starter，Micrometer 就幫你開 span，把 `traceId` 塞進 MDC，log 自動有。C# 的朋友，`Activity.Current` 在背景裡替你傳，`ILogger` 自己會讀。
> 這很方便，而且它們有一個共同的做法：**環境變數式的隱形傳遞。** MDC 是 `ThreadLocal`，`Activity.Current` 是 `AsyncLocal`，你不用傳，它就是在那裡。
> 可是隱形的東西，會在你沒注意的時候消失。`ThreadLocal` 的 trace id，在你把工作丟給另一條執行緒的那一刻，就跟你說再見了。**它不是不愛你，它只是不知道你搬家了。** 所以 Spring 的世界才有一整套「幫你把 MDC 複製過去」的包裝器。
> Go 沒有這種東西。沒有 `ThreadLocal`，goroutine 也沒有「目前的 span」。想要傳，就明明白白放在 `context.Context` 裡，一路當第一個參數傳下去。你一路傳，它就一路在；你沒傳，它就不在，不會半途默默消失。

> 所以 Go 這邊要自己接線。不是 starter，是大約十幾行的 `main.go`。這就是這集的代價，也是這集的好處：你看得到每一條線接去哪裡。

## 3:30 第一段：trace，請求一進來就開 span

【畫面】`cmd/api/main.go`，圈出 `NewTracerProvider`（第 104 行）和 `otelhttp.NewHandler`（第 219 行）。

```go
tp, err := telemetry.NewTracerProvider(os.Getenv("OTEL_TRACES_EXPORTER"), os.Stderr)
otel.SetTracerProvider(tp)
...
shop := otelhttp.NewHandler(handler.WithPaymentCallback(...), "shop", otelhttp.WithTracerProvider(tp))
```

> OpenTelemetry 在 Go 裡分兩半。API 是 `otel` 和 `trace`，程式碼用它開 span；SDK 是 `sdktrace`，決定 span 寫去哪裡。我們在 `main` 建一個 TracerProvider，裝成全域的。
> 然後把整個伺服器，用 `otelhttp.NewHandler` 包起來，放在最外面一層。每一個請求進來，它先開一個 span，把它放進請求的 ctx。之後 `RequestLog`、handler、service，拿到的 ctx 裡面都已經有這個 span。
> 要不要外部的 collector？不用。`OTEL_TRACES_EXPORTER` 預設是 `none`：span 照開，trace id 照有，只是沒人收。設成 `stdout`，span 變成 JSON 印到 stderr。以後要接真的 collector，改的是 `telemetry` 這一個檔，不是呼叫端。**這像在空房間裡開一場完整的會議：議程、紀錄、會議編號都有，只是沒人到。** 可是重點不是有沒有人到，是 id 已經存在，下一段 log 就用得上。

【畫面】`internal/service/order.go` 第 78 行。

```go
placeCtx, span := otel.Tracer("go-shop/service").Start(ctx, "order.place", ...)
placed, err := s.store.Place(placeCtx, lines)
```

> 我們也手動開一個子 span：`order.place`，包住真的跟 PostgreSQL 講話的那一段。它用的是傳進來的 ctx，所以自動掛在請求的 span 底下。以後有一個很慢的結帳，打開 trace 就看得到：時間是花在交易裡，還是花在別的地方。
> 注意名字：我開了 `placeCtx`，沒有蓋掉原本的 `ctx`。因為後面清購物車的 log 還要用原本的，不然它會寫著一個已經結束的 span。

> 當然，現在 trace 只有兩層：請求，加上下單。連資料庫呼叫和 Redis 都沒有各自的 span。可是先有兩層，總比一千兩百張便條紙好。這個缺口，我們記在附錄。

## 5:45 第二段：log 帶 trace id，一個 `slog.Handler` 就夠

【畫面】`internal/platform/telemetry/slog.go`，圈出 `Handle`（第 20 行）和 `WithAttrs`（第 29 行）。

```go
func (h logHandler) Handle(ctx context.Context, r slog.Record) error {
    if sc := trace.SpanContextFromContext(ctx); sc.IsValid() {
        r.AddAttrs(slog.String("trace_id", ...), slog.String("span_id", ...))
    }
    return h.inner.Handle(ctx, r)
}
```

> 現在每個請求都有 trace id 了，問題是怎麼讓 log 知道。答案是 `slog` 的 Handler：它是個 interface，我們寫一個，包住原本的 JSON handler。每一筆紀錄經過我們的時候，先看 ctx 裡有沒有 span，有，就多加兩個欄位。這個結構你應該很眼熟：拿一個、回一個，跟 middleware 一模一樣。
> 兩個地方要小心。第一，要用 `InfoContext`，不是 `Info`。`logger.Info` 沒有 ctx，我們沒東西可讀，它會安靜地、不帶 id 地寫出去。所以我們把 `RequestLog`、`Recover`、`writeError`（真正的失敗原因寫在這裡）和金流回呼的 log 都改成吃請求的 ctx。
> 第二個更陰險。`logger.With("order", 7)` 會呼叫 Handler 的 `WithAttrs`，它要回傳一個新的 Handler。如果你只是把這個呼叫轉給裡面那個，回來的就是**沒有包裝**的 handler：從那條 logger 寫出去的每一行，都沒有 trace id。**這個 bug 不丟錯誤，不讓測試變紅，它只是靜靜地不說話——跟半夜的客訴一模一樣。** 所以 `WithAttrs` 和 `WithGroup` 都必須回傳我們自己的型別，而且有測試守著。

> 我們現在的 log 終於有名字了：同一個請求裡，走 `*Context` 的每一行，共用一個 `trace_id`：請求紀錄、錯誤回應的原因、結帳的警告、金流回呼。拿著客訴那一個 id 去搜，一千兩百行，剩下那個請求自己的幾行。

## 7:30 第三段：metrics，標籤用路由樣式，不用路徑

【畫面】`internal/handler/observe.go`（第 23 行起的 `Instrument`）；瀏覽器打開 `/metrics`。

```text
http_requests_total{method="GET",route="/products/{id}",status="200"} 2
http_request_duration_seconds_count{method="GET",route="/products/{id}"} 2
```

> trace 和 log 回答「這一個請求發生什麼事」。可是老闆問的是「整體」：有幾個請求、多慢、多少失敗。那是 metrics。我們用 Prometheus 的 Go 套件，加兩個指標：請求次數，加請求時間的直方圖。`GET /metrics` 把它們用文字吐出來，Prometheus 定時來抓。
> 整集最容易踩的一行：**標籤。** 如果標籤是原始路徑 `/products/1`、`/products/2`……每一個商品 id，就是一條新的時間序列。更糟的是，掃描器從來不累，它可以替我們發明無限多條路徑：`/wp-admin`、`/.env`、一個隨機字串。每一條序列，指標系統都要記著。**我們的監控帳單，會成為這個晚上的第二個事故。**
> 所以標籤用 chi 的**路由樣式** `/products/{id}`。一百萬個商品，還是一條。沒有路由認領的請求，全部叫 `unmatched`，不管它是掃描器還是打錯字。（實際接線下，chi 的 `Mount` 會把這類請求標成 `/*`，我們在 `routeLabel` 把它也歸到 `unmatched`。）
> 有一個小細節：路由樣式要在請求跑完**之後**才讀。因為 chi 要等路由比對完，才知道是哪一條。所以 `Instrument` 先呼叫 `next`，再讀。它排在限流器**前面**，429 才算得到；panic 也用 `defer` 記成 500，再讓 `Recover` 去回應。被限流的 429 因為還沒走到路由，標籤是 `unmatched`。

## 9:00 這些東西在哪裡跑

【畫面】`cmd/api/main.go` 第 220 行起：`mux.Handle("GET /metrics", ...)`；終端機，`$env:OTEL_TRACES_EXPORTER="stdout"` 後 span 的 JSON 捲過去。

> 你可能在想：Jaeger 呢？Grafana 呢？Collector 呢？
> 一個都沒有。**今天的可觀測性平台，叫 stderr。** 這是刻意的：先確定 id 有進 log，指標有出來，再去想要把它們送到哪裡。接線是 `main` 的十幾行；送去哪裡，是上線之後才要決定的事。
> `/metrics` 掛在商店旁邊，不經過限流和 session，因為 Prometheus 不是訪客。實際部署的時候，這個路徑應該在內部的 port，不該跟商店一起暴露在外面。這一點我們寫在附錄。

> 最後是關機：span 是批次送出的，還在佇列裡的，程式結束前要 `Shutdown` 沖出去。`main` 裡有一個 `defer` 做這件事。可是我們現在關機的方式，還很粗糙——收到中斷就直接關伺服器。這個，下一集處理。

## 10:00 證明：兩件事

【畫面】`go test ./internal/handler -run "TraceID|Metrics" -v`，然後 `go test ./internal/platform/telemetry ./internal/service -run "Log|Span|Exporter|Observe" -v`，全綠。

> 第一件，log 裡有 trace id。測試把整條鏈接起來，跟 `main` 同一個順序：最外面 `otelhttp`，裡面是路由、`RequestLog`、`Instrument`。打一個請求，然後把 log 解析出來：log 裡的 `trace_id`，等於 handler 自己從 ctx 看到的那一個，而且有 `span_id`。
> 另外一組測試守著 Handler：有 span 的 ctx 有 id，`context.Background()` 沒有；`logger.With` 和 `WithGroup` 之後還是有。剛才說的那個安靜的 bug，如果有人把它改壞，測試會紅。
> 第二件，`/metrics` 有新指標。打兩次 `/products/{id}` 和一次不存在的路徑，然後讀 `/metrics`：`http_requests_total` 那個路由是兩次，`unmatched` 是一次 404，而且整個輸出裡**沒有**原始路徑 `/products/1`。測試走的是 `main` 同一種接線（`WithPaymentCallback` 的 `Mount`），另外一個測試證明被限流的 429 和 handler panic 的 500 也進得了 metrics。
> 再加一個：service 的測試證明 `order.place` 真的是請求 span 的子 span，下單失敗的時候狀態是 error。

## 11:45 三點收尾

> 好，我們收一下。
> **第一**，context 是 trace 的載體：請求一進來就開 span，放進 ctx，一路當第一個參數傳下去。Go 沒有隱形傳遞，所以它也不會半路弄丟。
