# 第 9 集｜庫存被佔（口播稿草稿 v0）

- 目標長度：12–13 分鐘（約 3,500 字口播）
- 本集唯一主概念：**`time.Ticker` 排程 + `context.WithTimeout` 逾時取消**：一個背景 goroutine 每隔一段時間掃一次，把逾時沒付款的訂單釋放、把庫存還回去；每一輪自己帶一個期限，卡住就被取消，下一輪重新來。重點對照：context 取代 `CancellationToken`，但它還帶著 deadline 與值
- 程式對應：tag `ep09`（`git checkout ep09`）
- 風格依 [style-guide.md](../style-guide.md)；【畫面】是剪輯提示，不唸出來。

> 現在是早上 9 點 47 分，距離老闆的訊息過了七分鐘，那台顯示器已經被一張沒人要的訂單佔了六十一個小時。
> 今天做三件事：訂單超過期限沒付款，就釋放它、把庫存還回去；用 `time.Ticker` 讓一個背景 goroutine 每隔一段時間做這件事；每一輪都用 `context.WithTimeout` 給它一個期限，卡住就取消。最後證明三件事：逾時的會被釋放、已付款的不動、單輪逾時會被取消。

## 1:40 C# 會怎麼寫（為什麼在 Go 行不通）

【畫面】左邊 ASP.NET Core：`BackgroundService`，`while (await timer.WaitForNextTickAsync(ct)) { await ReleaseExpiredAsync(ct); }`；或是 Hangfire 的 `RecurringJob`。Java 換成 `@Scheduled(fixedDelay = 60000)`。右邊是空的 `expiry.go`。

> C# 的朋友，你大概知道怎麼做：寫一個 `BackgroundService`，用 `PeriodicTimer`，每分鐘醒來釋放一次。Java 的朋友，`@Scheduled`，一行註解就好。
> 它們有一個共通點：**排程是框架幫你管的。** 框架決定什麼時候叫你、誰來取消你、關機時等不等你。你只需要寫「要做什麼」。
> 當然，這很方便。可是方便的代價是，那個「卡住」的情況你很少想到：`ReleaseExpiredAsync` 如果卡在一個鎖上呢？`PeriodicTimer` 會等你做完才算下一次；`@Scheduled` 預設也不會幫你限時。一輪卡住，後面每一輪都不會來，剛好是庫存最需要被釋放的時候。
> Go 的標準庫沒有 `BackgroundService`，也沒有 `@Scheduled`。它給你三樣零件：`time.Ticker`、`select`、`context`。自己組。

> 好消息是，組起來只有二十行。壞消息是，這二十行裡有兩行，你忘了寫，它就會默默漏水。

## 3:30 第一段：什麼叫「逾時沒付款」

【畫面】`db/migrations/00006_add_order_expiry.sql`，圈出 `expired_at`；`db/queries/orders.sql`，圈出 `ClaimExpiredOrder`。

> 先決定「逾時沒付款」怎麼判斷。我們已經有兩個欄位：`created_at` 是下單時間，`paid_at` 是第 7 集記下的付款時間。再加一個 `expired_at`：庫存還回去之後，蓋一個章，同一張訂單不會被釋放第二次。
> 條件寫成：`paid_at IS NULL AND expired_at IS NULL AND created_at < 截止時間`。沒付款、還沒釋放、而且夠老。

【畫面】`internal/repository/expiry.go`，`ReleaseOne`。

> 釋放一張訂單做三件事：把每一個品項的數量加回庫存，蓋 `expired_at` 的章，然後提交。三件事在同一個交易裡：要嘛庫存還了、章也蓋了，要嘛都沒發生。不會出現「庫存還了，但訂單還是未付款」，然後下一輪再還一次。
> 注意我們**一次只處理一張訂單**。為什麼？交易短，鎖的時間短；而且呼叫的人可以在兩張之間停下來，時間到了就停。
> 撈訂單的 SQL 後面還是 `FOR UPDATE SKIP LOCKED`，跟上一集同一招。如果某張訂單這一刻剛好有付款回呼在更新，我們跳過它，不等它：下一輪再看。已經付了錢的，就不會被我們釋放。
> 鎖的順序也跟結帳一樣，品項依商品編號排好。結帳和釋放同時發生，也不會互相等對方。

> 釋放庫存其實比扣庫存簡單：加法不需要先檢查，沒有人會把庫存加成負數。這大概是整個系列裡，我們寫完資料庫程式，覺得太簡單而有點不安的唯一一次。
> 不安是對的：前提是同一張訂單只能被加一次，所以才需要那個 `expired_at` 的章。

## 5:45 第二段：`time.Ticker` 加 `select`

【畫面】`internal/service/expiry.go`，`ExpiryJanitor.Run`。

```go
func (j *ExpiryJanitor) Run(ctx context.Context) {
    ticker := time.NewTicker(j.cfg.Interval)
    defer ticker.Stop()
    for {
        j.Sweep(ctx)
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
        }
    }
}
```

> 這就是排程的全部。`time.NewTicker` 每隔一段時間，往 `ticker.C` 這條 channel 丟一個東西；`select` 等兩件事，時間到了，或是 `ctx` 被取消了。取消了就 `return`。這個形狀你在上一集看過，這一集只換了裡面做的事。
> `defer ticker.Stop()` 不能忘。Ticker 是一個有計時器的東西，不停掉，它會一直在背景跑。這是 Go 的版本的「忘了 Dispose」。

> 還有一個細節。這裡的間隔、期限、還有「現在幾點」，全都是設定的欄位，不是寫死的。`ExpiryConfig` 裡面有一個 `Now`，預設是 `time.Now`。**時鐘也是一個可以注入的依賴。** 測試的時候，我們不是真的等十五分鐘，而是讓「現在」往後跳一小時。C# 的朋友，這就是你熟悉的 `TimeProvider`，只是我們用的是一個普通的函式欄位，沒有介面、沒有容器。

> 如果你問，為什麼不乾脆把時間寫在測試裡 `time.Sleep(15 * time.Minute)`？
> 因為我們的 CI 還想在今年之內跑完。

## 8:20 第三段：每一輪自己帶期限

【畫面】`Sweep`，圈出 `context.WithTimeout`。

```go
roundCtx, cancel := context.WithTimeout(ctx, j.cfg.RoundTimeout)
defer cancel()
// ...
id, ok, err := j.store.ReleaseOne(roundCtx, cutoff)
```

> 這是這一集真正的重點。`context.WithTimeout` 拿一個 `ctx`，回傳一個新的 `ctx`，加上一個期限。三十秒後，它自己會變成「已取消」。
> C# 的朋友，這看起來像 `new CancellationTokenSource(TimeSpan.FromSeconds(30))`。像，但有一個差別：Go 的期限**住在 context 裡面**，不是住在另一個你要自己記得傳的 token 旁邊。`ReleaseOne` 把它交給資料庫驅動，驅動在等回應的時候，同時也在看這個期限。時間到了，資料庫呼叫自己就回來了，回的錯誤是 `context.DeadlineExceeded`。
> 我們在 `Sweep` 裡把這個錯誤分成三種。`DeadlineExceeded` 而且外面的 `ctx` 還好好的：這一輪超時了，記一條警告，回去等下一輪。其他錯誤：記錄，結束這一輪。外面的 `ctx` 被取消了：這是關機，不是故障，不要吵。
> `defer cancel()` 也不能忘，跟 `defer ticker.Stop()` 一樣：`WithTimeout` 會佔著一個計時器，沒呼叫 `cancel` 就得等期限到。

> 我們的清潔工對卡住的同事很有原則：三十秒，不等了，下一位。卡住的那一輪被砍掉，下一輪照常開始，沒有一輪能卡死整個排程。

【畫面】`cmd/api/main.go`：兩個 worker 共用一個 `workerCtx`，一個 `defer` 取消並等兩個都結束。

> 啟動它的方式跟上一集一樣：誰啟動，誰停；`context` 叫它停，channel 確認它停了。這次有兩個 goroutine，所以是同一個 context、同一個 `defer`。

## 10:00 證明：三件事

【畫面】`go test ./internal/service -run Expiry -v`，然後 `go test -tags=integration ./internal/repository -run Expiry -v`，全綠。

> 第一件，逾時的訂單會被釋放。我們下一張單，買兩個商品加上最後一台顯示器；然後讓時鐘往後跳一小時，掃一輪。結果：兩個商品的庫存都回到原本的數字，顯示器回到一，訂單的 `expired_at` 有值。再掃一輪：釋放的數量是零，庫存不會再加一次。
> 第二件，已付款的不動。同樣下一張單，用第 7 集的 `Record` 記一筆付款，時鐘往後跳一小時，掃一輪。結果：零張被釋放，庫存維持被扣掉的樣子。付了錢的人，不會被我們的清潔工拿走訂單。
> 順便一個反例：沒付款、可是才剛下的訂單，用真的時鐘掃，也不會被動。我們不是看到未付款就釋放，是看到「未付款而且夠老」。

> 第三件，單輪逾時會被取消。這個測試用一個假的 store，它收到呼叫就永遠等下去，只等 `ctx`。我們把單輪的期限設成二十毫秒。結果：`Sweep` 在期限到的時候回來了；假 store 看到的錯誤是 `DeadlineExceeded`；整個測試設了兩秒的保險，沒回來就失敗。
> 這個測試如果沒有那一行 `WithTimeout`，就會卡到兩秒的保險才失敗。我們靠它知道，那一行真的有用。

> 還有一個：`Run` 在 `ctx` 取消之後一定會回來。跟上一集同一種測試。
