## 1:40 C# 會怎麼寫（為什麼在 Go 行不通）

【畫面】左邊 Visual Studio：`[RateLimit("per-ip")]`、`app.UseRateLimiter()`、一個繼承 `ActionFilterAttribute` 的類別。

> C# 的朋友，這個早上你大概這樣過：
> 在 controller 上貼一個 `[Authorize]`，寫一個 `ActionFilter`，在 `Program.cs` 裡 `app.Use...` 一排。
> Java 的朋友，就是 Servlet `Filter` 加 `FilterChain`，或者 Spring 的 `HandlerInterceptor`。
> 這些都很好用。可是它們有個共通點：**你要先學一套框架自己的規則**。filter 什麼時候跑？順序誰決定？貼在 class 上跟貼在 method 上誰先？答案都在文件的某一頁。

> 好，Go 的標準庫怎麼說？它說：一個 handler 就是一個有 `ServeHTTP(w, r)` 的東西。
> 要加功能？寫一個函式，**收一個 handler，回傳一個 handler**。
> 就這樣。沒有第二條規則。
> 這說明什麼？說明 filter 在 Go 裡不是一個「框架概念」，只是**一個回傳函式的函式**。好那我們來看。

## 3:30 第一段：middleware 就是函式包函式

【畫面】`internal/handler/middleware.go` 的 `RateLimit`，圈出簽名與最後一行。

```go
func RateLimit(limiter Limiter, logger *slog.Logger) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            ok, retryAfter := limiter.Allow(clientIP(r))
            if !ok {
                // 429，然後 return：不呼叫 next
                return
            }
            next.ServeHTTP(w, r)
        })
    }
}
```

> 看這個簽名：`func(http.Handler) http.Handler`。吃一個 handler，吐一個 handler。
> 裡面這個新的 handler 做三件事裡的一件：在 `next` **之前**做點事、在 `next` **之後**做點事、或者**根本不呼叫 `next`**。
> 我們的限流就是第三種：判斷這個 IP 已經用光額度，就直接回 429，然後 `return`。**不呼叫 `next`，就是擋下來**。對照 C#，就是不呼叫 `await next(context)`；對照 Java，就是不呼叫 `chain.doFilter`。

【畫面】動畫：三層洋蔥，請求從外往內，回應從內往外。接著 `TestChainOrder` 的輸出：`first in, second in, second out, first out`。

> 那一串 middleware 怎麼串？`r.Use(a, b, c)`，等於 `a(b(c(router)))`。**像包洋蔥**：請求從最外層進去，一層一層剝到路由；回應再從最裡面一層一層包出來。
> 我們寫了一個測試叫 `TestChainOrder`：兩個只會記錄「進來、出去」的 middleware，印出來是 `first in, second in, second out, first out`。看到了嗎？進去的順序，跟出來的順序**剛好相反**。
> 這就是為什麼順序很重要。我們的順序是：請求紀錄、panic 復原、限流、session。
> 為什麼限流在 session 前面？因為如果倒過來，一千次狂打會**幫你建一千個 session**。攻擊者免費拿到記憶體。限流擋在前面，洪水在限流這一關就停下來。

## 5:45 第二段：限流與 token bucket

【畫面】`internal/platform/ratelimit/ratelimit.go`，圈出 `Allow`。

> 限流本身怎麼算？我們用最經典的做法：**token bucket，令牌桶**。
> 想像每個 IP 有一個桶子，桶子最多裝 20 個令牌，每秒補 10 個。打一次 API 拿走一個。桶子空了，就 429，等到有令牌再放行。
> 平常的客人，一個頁面打個五六支 API，桶子根本不會空。腳本一秒打一千次呢？前 20 次放行，剩下的……好，有一點禮貌，我們叫它「等一下」。

【畫面】429 回應的 headers：`Retry-After: 1`。

> 429 要帶一個 `Retry-After`，告訴對方幾秒後再來。這不是客氣，是給好的客戶端一個機會：按照這個時間等，不要再狂打。
> 當然，這個限流器有三個地方值得講。
> 第一：**用 mutex 保護 map**。很多 goroutine 同時進來，同時改同一個 map，Go 會直接讓整個程式倒掉（那是 fatal error，連 Recover 都接不住）。我們用一個 `sync.Mutex`，鎖的範圍就是那幾行。併發的完整故事在後面幾集。
> 第二：**要清掉閒置的桶子**。不清，一百萬個 IP 各打一次，記憶體就留著一百萬個桶子。`sweep` 會把已經補滿的桶子刪掉——補滿的桶子，跟沒有桶子，是一樣的。
> 第三：**時鐘是注入進來的**。測試不用 `time.Sleep`，用一個假時鐘，往前撥 1 秒就是 1 秒。測試快，而且不會因為機器忙而偶爾紅燈。

【畫面】IP 的取法：`net.SplitHostPort(r.RemoteAddr)`，旁邊一行劃掉的 `X-Forwarded-For`。

> 還有一個陷阱：「這個 IP 是誰」。我們用連線的 `RemoteAddr`，**不看 `X-Forwarded-For`**。為什麼？因為那個 header 是客戶端自己寫的。他每次都寫一個新的 IP，我們每次都當他是新客人。
> 這個設計好像很有道理哦——「信 header 才抓得到真實 IP」——不對，這叫把門鑰匙放在門口的地墊底下。真的放了反向代理，要信任哪一層，是部署時才決定的事，之後的集數再講。

## 8:15 第三段：session，還有 context

【畫面】`Session` middleware，圈出 `context.WithValue` 與 `SessionID(ctx)`。

> 限流擋掉了壞客人，接下來要認得好客人。
> session 的做法很樸素：客人第一次來，我們發一個隨機的 id，放進 cookie；下次他帶著 cookie 回來，我們就知道是同一個人。
> id 長 32 個十六進位字，來自 `crypto/rand`——**不是** `math/rand`。一個猜得到的 session id，等於把別人的帳號送出去。cookie 設 `HttpOnly`，JavaScript 讀不到，XSS 偷不走；`SameSite=Lax`，別的網站不能偷偷幫你送請求。

> 好，session id 拿到了，後面的 handler 怎麼知道？Go 的答案是 **`context`**。
> middleware 把 id 用 `context.WithValue` 放進請求的 context，後面的程式用 `SessionID(ctx)` 拿。
> 注意那個 key，是一個**自己定義的、不匯出的型別**。這樣別的套件就算也用字串 `"session"` 當 key，也撞不到我們。對照 C#，這比較像 `HttpContext.Items`，只是它有型別保護；Java 則像 `request.setAttribute`。

【畫面】`SessionStore` 介面：兩個方法 `Create`、`Exists`。

> 還有一件事：**session 存在哪**？現在是一個 in-memory 的 map。重啟就沒了，換一台機器也是空的。
> 沒關係，這集故意的。看 `SessionStore` 這個介面，只有兩個方法，而且它是**宣告在 handler 裡**，不是宣告在 map 那一邊。為什麼？等下一集你就知道了。

## 10:15 證明：同一個 IP，一千次

【畫面】`internal/handler/middleware_integration_test.go`，`TestFloodFromOneIPIsMostlyRejected`。

> 光說不練，只是一份有旁白的投影片。這集的事故是「一個 IP 一千次」，所以我們的測試，就是**同一個 IP 打一千次**。
> 不是呼叫函式，是起一個真的 HTTP server，走真的 TCP，一千個請求一個一個打進去。
> （測試用較小的桶子：容量 10、每秒補 5 個，跑起來比較快。）結果會被我們算出一個**上限**：桶子的容量，加上這段時間補的令牌。通過的請求不可以比這個多。

【畫面】執行 `go test -tags=integration -run Flood -v ./internal/handler`，輸出 `ok=10 limited=990`。

> 一千次裡面，10 次通過，990 次被擋。（這個數字會跟著設定與機器速度浮動，測試檢查的是上限，不是固定值。）
> 然後再來一個：二十條 goroutine 同時打，上限還是成立（CI 上加 `-race` 才是 mutex 的真正證明）。
> 最後，我們故意讓某個 handler 去 `panic`。在單元測試裡，你以為整個連線會斷掉？不會。`Recover` 這個 middleware 接住它，回一個我們熟悉的 `internal_error`，跟第 3 集的錯誤同一種形狀，而且 panic 的內容只寫進 log，不會送給客人。

【畫面】三個終端機分頁：`curl -i /products`（看到 Set-Cookie）、迴圈 200 次（200 … 429）、再打一次看到 `Retry-After`。

> 現在是早上 11 點 40 分。老闆再打開 log，那位客人的來源 IP 下面，一整排 429。
> 他問：「所以這個客人，現在被我們擋住了？」我說：「對，而且他拿到了一張寫著什麼時候可以再來的紙條。」

## 11:45 三點收尾

> 好，我們收一下。
> **第一**，Go 的 middleware 就是 `func(http.Handler) http.Handler`：函式包函式。前、後、或根本不呼叫 `next`，三選一。順序像洋蔥，進去跟出來剛好相反。
> **第二**，限流用 token bucket：容量決定突發、補充速度決定長期速率；記得用鎖保護、清閒置的桶、時鐘用注入的，而且不要信 `X-Forwarded-For`。
> **第三**，session 是一個隨機 id 加 cookie，`context` 是 middleware 把值交給後面程式的管道，key 要用自己的型別。
>
> 老闆的下一則訊息，是一張截圖：一位客人加了三件東西進購物車，然後我們重新部署，購物車是空的。
