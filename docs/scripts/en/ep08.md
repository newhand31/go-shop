# Episode 8 | The email that never left (voice-over draft v0, English channel)

- Target length: 11–13 minutes (about 1,600 spoken words plus screen-only beats and code on screen)
- The one main concept: **the outbox pattern, plus a goroutine you own**: "send a confirmation email" is written in the same database transaction as the order; a background goroutine picks it up later and retries until it works. A goroutine has no `Task` to await, so whoever starts it must cancel it and wait for it to finish

## 0:50 Time anchor

> It's 10:12 p.m., seven minutes after support's first message, and thirty-seven customers are refreshing an empty inbox.
> Three things today: write "send this email" into the same transaction as the order; start a background goroutine that picks it up and sends it, retrying on failure; and prove two things, that a failed send is retried, and that a rolled-back order leaves no email request behind.
> And we learn one thing: **in Go, nobody cleans up a goroutine for you. You decide when it stops, and you wait until it really has.**

## 1:40 How we'd do it in Spring (and why Go won't play along)

【畫面】Split screen: left, a Spring `@Transactional` service method that calls `orderRepository.save(order)` and then `mailSender.send(msg)`; or `@Async`. Right, an empty `outbox.go`.

> Coming from Java, you probably reach for one of two things. Option one: save the order, then send the mail, inside the `@Transactional` method. If the mail fails, the order is already saved: you can't roll it back, and if you return an error the customer just orders again. And while the mail goes out, your transaction is still open and your row locks are still held. You are making a phone call from inside a lock.
> Option two: `@Async`, or in C# `Task.Run`, fire and forget. Restart the process at the wrong second and the email vanishes. No record that it was ever supposed to exist.
> Sure, you can add `@Retryable`, or Hangfire in .NET. But those solve "how do I retry a send". They don't solve the real problem: **"the order is saved" and "the email must go out" are two writes, and the process can die between them.**
> That problem has a name: the dual write. Two places, and nothing guarantees both succeed.

> Go doesn't fix that either. So we change the question: don't write two places. Write one.

## 3:30 Part one: write the promise in the same transaction

【畫面】`db/migrations/00005_add_outbox.sql`, circling `payload jsonb`, `sent_at timestamptz`, `attempts`.

> An outbox is exactly what it sounds like: a table where each row says "this thing is waiting to be done". Ours has a topic, a JSON payload, an attempt counter, a next-try time, a sent time, and the last error.

【畫面】`internal/repository/orders.go`, the end of `Place`.

```go
payload, err := confirmationPayload(order)
// ...
if err := q.InsertOutbox(ctx, dbgen.InsertOutboxParams{Topic: TopicOrderConfirmation, Payload: payload}); err != nil {
    return Order{}, fmt.Errorf("insert outbox: %w", err)
}
if err := tx.Commit(ctx); err != nil {
```

> Look where `InsertOutbox` sits: right before `Commit`, on the same `tx`. Remember `Begin` plus `defer Rollback` from episode 6? It earns its keep again. The order, its lines, and the outbox row live or die together. All of it happens, or none of it does.
> We do not send anything here. There's no network call on the checkout path. The mail provider can be down for ten minutes and checkout doesn't lose a millisecond.
> And no matter which second the process dies in, we never get "order saved, nobody remembers the email". The promise exists exactly as long as the order does.

## 5:45 Part two: a background goroutine does the sending

【畫面】`internal/service/outbox.go`, the `Mailer` interface.

```go
type Mailer interface {
    SendOrderConfirmation(ctx context.Context, orderID, totalTWD int) error
}
```

> First, the interface. One method, and it's **defined next to the code that uses it**, not next to the code that sends mail. The real sender, the one that only logs, and the fake in the tests all fit because they have this method. Nobody writes `implements`. Java folks: picture `MailSender` living in the module that calls it, not in the SMTP module.

【畫面】`repository/outbox.go`, `Dispatch`; and `db/queries/outbox.sql`, circling `FOR UPDATE SKIP LOCKED`.

> The query that picks rows has a tail you may not have seen: `FOR UPDATE SKIP LOCKED`. It means: I lock these rows; anyone else who sees a locked row skips it. No waiting, no double sends. Run two workers someday and a given email still goes to exactly one of them.
> Success: set `sent_at`. Failure: add one to `attempts`, store the error, compute when to try again: one second, two, four, capped at five minutes. After eight failures the row stays in the table for a human, and the worker leaves it alone.

【畫面】`OutboxDispatcher.Run`.

```go
func (d *OutboxDispatcher) Run(ctx context.Context) {
    ticker := time.NewTicker(d.cfg.Interval)
    defer ticker.Stop()
    for {
        d.RunOnce(ctx)
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
        }
    }
}
```

> And here's the goroutine's loop. A `time.Ticker` fires every interval. The `select` waits for two things: the tick, or `ctx` being cancelled. Cancelled? `return`.
> Notice `Run` itself blocks. It doesn't start a goroutine. Whether it runs in the background is the caller's decision.

## 8:20 Part three: whoever starts it, stops it

【畫面】`cmd/api/main.go`, circling `workerCtx, stopWorker := context.WithCancel(ctx)` and `<-workerDone`.

```go
workerCtx, stopWorker := context.WithCancel(ctx)
workerDone := make(chan struct{})
go func() {
    defer close(workerDone)
    dispatcher.Run(workerCtx)
}()
defer func() {
    stopWorker()
    <-workerDone
}()
```

> This is the biggest difference from what you know. In C#, a `Task` is a thing. You hold it, you can `await` it, you hand it a `CancellationToken`, and it tells you how it ended. In Java, a `Future` does the same. Go's `go` keyword **returns nothing**. You press it, the goroutine runs, and nobody is holding a handle.
> A goroutine with no handle is a balloon with no string: letting go is easy, getting it back is the part you should have planned.
> No handle? Build one. We build two: a `context` to say "stop", and a channel to hear "I have stopped". `defer close(workerDone)` is the goroutine's last words.
> Before main exits: `stopWorker()`, then `<-workerDone`. That `defer` is registered after `pool.Close`, so it runs first. The worker is always gone before the pool is. Reverse it and the worker spends its last moments querying a closed pool and complaining about it in the background.
> Forget to wait and what happens? The program still exits. Somebody just gets cut off mid-email. One more detail: after the send, the "sent" mark is written with `context.WithoutCancel`, so even during shutdown it lands. Otherwise the next start sends it again.

> Last thing: the real mail provider is replaced by a `logMailer` that only logs. The shop has no customer accounts yet, so no customer email address either. For now it says "I would send this." Real sending, real recipients: later.

## 10:00 The proof: a failed send retries, a rollback leaves nothing

【畫面】`go test -tags=integration ./internal/repository -run Outbox -v`, all green.

> First test: `TestOutbox_FailedSendIsRetriedUntilItWorks`. The test mailer fails twice, then works. The worker looks every five milliseconds, and the backoff is set to zero, so we don't wait around. Result: the mailer was called three times, `attempts` is three, the last error is cleared, `sent_at` is set. Run another pass and the mailer is not called a fourth time. Sent means sent.
> The end of that test is two lines: `cancel()`, then `<-done`. **Make sure the worker has really stopped before looking at the final state.** Otherwise the test itself is a goroutine nobody collected.
> Second test: `TestOutbox_RolledBackOrderLeavesNoOutboxRow`. We wrap a transaction whose `Commit` always fails, and place an order. Result: zero rows in `outbox`, zero in `orders`, stock back at 10. **The email promise was taken back along with the order.**
> One more: a mailer that always fails, `MaxAttempts` of three, six passes. The mailer is called three times. The row stays, and it says why: `smtp down`.

> The unit tests use a fake mailer and a fake store, and `Run` must return after its context is cancelled. If it doesn't within two seconds, the test fails. A leaking goroutine gets caught in CI, not in production.

> It's 10:58 p.m. Support writes: "Those thirty-seven? Sent."
> I say: "They were in the table the whole time. Just waiting for the mail provider to wake up."

## 11:45 Three takeaways

> Let's wrap up.
> **One**, "save the order" and "send the email" are two writes, and nothing guarantees both. Make the second one a row in the same transaction and there's only one write left.
> **Two**, a goroutine has no `Task`. Whoever starts it cancels it with a `context` and waits for it with a channel.
> **Three**, a failed send isn't an exception. It's the normal path: record the error, schedule the next try, retry. And put a ceiling on it.
>
> The boss's next message: "That monitor says one left. Nobody could buy it all night."
> Ship it small, ship it tested. See you at the next incident.

## Appendix B: open questions

- The shop has no customer accounts or email addresses yet, so there is no recipient; `logMailer` only logs. Do not imply real mail is being sent.
- The architecture doc says "outbox + NATS/RabbitMQ + worker"; this episode is a database-polling worker only, with no message broker.
- `Dispatch` keeps its transaction open while sending (that's what holds the `FOR UPDATE SKIP LOCKED` locks). If sending gets slow, change it to claim, send, then write back; at this volume it is not handled.
- Delivery is at-least-once: if the process dies after the email goes out but before `sent_at` is written, or a database error rolls back the whole batch, the next pass sends it again. Receivers must tolerate a repeat. Same theme as episode 7's idempotency key; not expanded here.
- Rows that hit `MaxAttempts` (default 8) are never retried automatically, and there is no alert or manual resend tool.
- Backoff is computed with the database's `now()`, so it doesn't depend on the Go clock.
- No load test and no multi-worker test: the behaviour of `SKIP LOCKED` rests on SQL's own semantics, with no test of it here.
- The sign-off is the fixed line from §6.1.
- The next-episode teaser only states the symptom (stock held by unpaid orders), not the fix.
