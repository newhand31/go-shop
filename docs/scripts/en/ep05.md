## 0:50 Time anchor

> It's 2:20 p.m., three hours before the evening sale, and 100% of carts are lost on every redeploy.
> Three things today: move sessions and carts into Redis; separate "how we store it" from "what we need to store"; and prove it with two API instances, with a customer jumping between them and the cart staying put.
> And we learn one thing: **in Go, interfaces are implicit, and the code that uses a thing is the one that defines the interface.**

---

## 1:40 How we'd do it in Spring (and why Go won't play along)

【畫面】Split screen: left, `interface CartRepository`, `class RedisCartRepository implements CartRepository`, a `@Repository` sticker. Right, an empty `cart.go`.

> If you're coming from Java, this afternoon goes like this.
> Write `interface CartRepository`. Write `class RedisCartRepository implements CartRepository`. Put `@Repository` on it, and let Spring wire it in. C# folks: `ICartRepository`, a colon, and `AddScoped`.
> Notice the order. The interface comes first, and the implementation has to sign it: "I implement this." That signature is written on the implementation's side.

> Sure, that's a reasonable design. But it has a side effect. The interface tends to sit next to the implementation, and it tends to have ten methods, because it was designed around what the thing can do, not around who needs it.
> So a class that only needs to read a cart depends on an interface with ten methods. And a test double has to implement all ten. Who wouldn't want that in their codebase?

> Go says: no signature. If you have the methods, you fit. Let's go look.

---

## 3:30 Part one: the consumer owns the interface

【畫面】`internal/service/cart.go`, the top of the file, circling `CartStore`.

```go
// CartStore is what the cart logic needs from storage...
type CartStore interface {
    Items(ctx context.Context, cartID string) (map[int]int, error)
    SetItem(ctx context.Context, cartID string, productID, quantity int) error
    RemoveItem(ctx context.Context, cartID string, productID int) error
}
```

> Look at this interface. It's declared in the `service` package, which is the **consumer**. And it has three methods: exactly the three the cart logic uses.
> That's our project rule: **define the interface where it's used.** The consumer says, "I need these three things." Whoever can do those three things is welcome.

【畫面】`internal/repository/cart.go`, scrolling the whole file. Circle the fact that there is no `implements`, and no mention of `CartStore`.

> Now the other side: `repository.Carts`. Search that file for the word `CartStore`. You won't find it.
> It's a plain struct with a Redis client and three methods whose names, parameters and results happen to match. It doesn't know who will use it. It doesn't know the `service` package exists.
> That's an implicit interface. **You don't sign anything. You just have the methods.**

【畫面】`cmd/api/main.go`, the two `var _ service.CartStore = (*repository.Carts)(nil)` lines.

> So who checks the fit? **The place where the two meet.** `main`. We put two lines there, one per seam, like `var _ service.CartStore = (*repository.Carts)(nil)`. It means, "compiler, please confirm this type satisfies that interface."
> I delete `RemoveItem` from `Carts` and build. Red: `missing method RemoveItem`. The check is still there. It just moved from the one who declares to the one who wires.

## 5:50 Part two: Redis, moving state out of the process

【畫面】The `SetItem` code; next to it, `redis-cli` running `HGETALL cart:...`.

> Now the implementation. The cart is a Redis **hash**: the key is `cart:` plus the session id, each field is a product id, each value is a quantity.
> Why a hash instead of one JSON blob? Adding one product touches one field. No "read the whole cart, change it, write it all back." Two tabs adding different products can't overwrite each other.
> On write we use a pipeline, so "set the field" and "reset the seven-day expiry" travel in one round trip. A cart nobody touches disappears by itself. Every add or change pushes the expiry forward.

> Sessions move too. In episode 4 they lived in a map in memory. Now it's `session.Redis`: `Create` uses `SET`, `Exists` uses `EXPIRE`, which extends a live session and answers false for a missing one.
> Look at `main`: **`session.NewMemory` becomes `session.NewRedis`.** The handler didn't change by one line. Why? Because it only ever declared "I need `Create` and `Exists`." Remember when I said "next episode will answer that"? This is that.
> Sure, we could swap Redis for something else the same way, one line in `main`. But don't pre-build interfaces for "someday". You extract one when you have a second implementation, or a test that needs a double.

## 8:20 Part three: small interfaces, small tests

【畫面】`internal/service/cart_test.go`, `memCartStore`; next to it `fakeCarts` in `internal/handler/cart_test.go`.

> My favorite part. A fake store for the tests? Three methods, twenty lines, one map. No mocking framework. No generator.
> The handler is the same: it needs three methods from its `Carts`, so `fakeCarts` is a few return values. Want to test that a failing service never leaks internals? Make `fakeCarts` return an error that contains an internal IP, then check the response doesn't.
> Small interface, small fake, small test. That's not luck. It's what you get when the **consumer** decides how big the interface is.

【畫面】`service.Catalog`: just `List`. `*ProductService` is passed straight into `NewCartService`.

> One more. The cart needs product names and prices, so it asks for a `Catalog`: one method, `List`. We pass in the `ProductService` from episode 2. It has never heard of `Catalog`. It just happens to have `List`.
> That's why Go code can often be connected after the fact, without reopening the old code.

---

## 10:10 The proof: switch machines, keep the cart

【畫面】`internal/handler/cart_integration_test.go`, the two test names.

> Talking without proving is a slide deck with a voice-over. So we wrote two integration tests, with a real Redis from testcontainers.
> First, replay the incident. Two API instances, each keeping state in **process memory**, one browser with one cookie jar. Add an item on A: A sees it. Switch to B: **an empty cart.** The test passes, which means we reproduced the bug.
> Second, the fix. Same two instances, but sessions and carts live in Redis. Add two items on A, see two on B, delete one on B, go back to A: one left. A different browser can't see this cart at all.
> Expiry has its own test too: when it's over it's over, and each session use, and each cart write, pushes it forward.

【畫面】`go test -tags=integration ./...` is green; then two terminals, two API instances; `curl -c jar -b jar` adds on 8080 and reads the cart on 8081.

> It's 5:50 p.m. Support writes: "That customer is back. He bought three things this time."
> I ask: "How many servers did he hit?" Support says: "No idea."
> Exactly. He doesn't need to know, and neither do we.

---

## 11:45 Three takeaways

> Let's wrap up.
> **One:** Go interfaces are implicit: matching methods are enough, and there is no `implements`. The check is still there, it moved to where the pieces meet, the `main` that wires them.
> **Two:** define the interface in the consumer, and keep it small: only the methods you use. Don't abstract for "someday"; extract when there's a second implementation or a test that needs a double.
> **Three:** keep state out of the process. Sessions and carts in Redis, a hash for the cart, an expiry for what nobody wants. The handler never noticed.
>
> The boss's next message: "We had one item left, and we sold three."
> Next episode: **overselling.**
> Ship it small, ship it tested. See you at the next incident.

## Appendix B: open questions

- Prices come from the catalog at read time; price-locking at checkout belongs to a later episode.
- The cart view lists the whole catalog once (same shortcut as the single-product lookup in episode 3); a batched query can replace it.
- Redis in docker compose has no password or TLS; it is local-only, and the script doesn't mention it.
- Merging a guest cart into an account cart is out of scope for the series.
- The cart TTL (7 days) is longer than the session TTL (24 h), and the cart key is the session id, so in practice a cart lives as long as its session; align them later if carts should outlive sessions.
- The session cookie's `Max-Age` and Redis's sliding expiry are not synchronized (same as episode 4); re-issuing the cookie on use would fix it.
- The cold open needs two API instances on `ep04` (set `PORT`); that version has no `/cart`. When recording, either temporarily put memory stores back into the ep05 `main`, or show the output of the first integration test.
- The sign-off is the fixed line from §6.1.
