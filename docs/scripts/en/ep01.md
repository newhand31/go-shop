## 1:30 How we'd do it in Spring (and why Go won't play along)

【畫面】Split screen: left, the Spring Initializr page; right, the empty Go folder.

> If you're coming from Java, tonight goes like this.
> Open Spring Initializr. Tick "Spring Web". Click Generate. Unzip.
> Three seconds later you have an `Application` class with `@SpringBootApplication` on it, an `application.properties`, and a framework that is already scanning your packages for anything with an annotation.

【畫面】Spring code, three classes. Circle `@RestController`, `@Service`, `@Repository`, and a constructor that takes a `ProductRepository`.

> You write a `ProductController`, a `ProductService`, a `ProductRepository`. You put a sticker on each one. Spring finds the stickers and builds the object graph for you.
> Who creates the controller? The container. Who creates the container? Spring Boot. Who creates Spring Boot? `SpringApplication.run`. Who calls that? `main`. [pause] Oh look. There was a `main` the whole time. It was just hiding behind four hundred auto-configurations.
> Sure, none of this is wrong. In a big codebase the container earns its keep. But at midnight it has one small problem: you can't see who created what. When it breaks, you're debugging an object graph you've never actually looked at.
> C# folks, same story, different sticker: `builder.Services.AddScoped<IProductRepository, ProductRepository>()`.

> So what does Go give us? No built-in container. No base controller class. No project wizard.
> It gives us a `main` function, and an ancient technology called "calling the constructor yourself".
> What does that tell us? It tells us we're wiring this by hand tonight. Sounds primitive. Let's go look, because it's nicer than it sounds.

## 3:30 Part one: project layout (`cmd/` and `internal/`)

【畫面】Editor, file tree expanded: `cmd/api/main.go`, `internal/handler`, `internal/service`, `internal/repository`, `internal/platform`.

> Let's start with folders.
> `cmd/api/` is the entry point. `main` lives here. Later we'll add `cmd/worker/`, which is why this is a folder and not a single file.
> `internal/` is a rule the Go compiler enforces: packages under `internal/` can only be imported by code inside this module's tree. Anybody else gets a compile error.
> Java has package-private, but that stops at one package; sub-packages are strangers. Go's `internal/` protects a whole directory tree. If you've used Java modules, it's closer to "this package is not exported", minus the `module-info.java`. C#'s `internal` does the same job per assembly.

【畫面】A throwaway module tries to import `github.com/newhand31/go-shop/internal/service`. The terminal shows `use of internal package ... not allowed`.

> Under `internal/` we have three layers, and traffic goes one way: **handler calls service, service calls repository.**
> Handler speaks HTTP. Service holds the business rules. Repository fetches data. Calling backwards? No. Skipping a layer? Also no.
> Who enforces that? Tonight, me and my discipline. The same discipline that answered the boss with an emoji. So, for now, code review enforces it.

> The takeaway: **in Go, folders are design.** There's no separate namespace concept. A folder is a package, and a package is a boundary.

## 5:30 Part two: wiring by hand (no container, just `main`)

【畫面】`cmd/api/main.go` full screen; highlight lines 25–27.

```go
repo := repository.NewMemoryProducts()
svc := service.NewProductService(repo)
h := handler.New(svc, logger)
```

> Three lines.
> Line one creates the repository. Line two hands it to the service. Line three hands the service to the handler.
> That's the whole dependency injection. No annotations, no container, no component scan. Is it a singleton or request-scoped? There's exactly one scope here: **whatever you wrote in `main`.**
> The constructor takes what it takes, and the compiler checks it. Forget an argument: red squiggle. Pass the wrong type: red squiggle.
> In Spring, a missing bean shows up when the application boots: `No qualifying bean of type ProductRepository`. In Go it shows up before there's a binary at all. And I'll take a red squiggle at 11:50 p.m. over a stack trace at 9:01 a.m. any day.

【畫面】Switch to `internal/service/product.go`; highlight lines 12–14.

> One more detail. The service needs data. How does it ask for it?

```go
type ProductStore interface {
	List(ctx context.Context) ([]repository.Product, error)
}
```

> Notice who declares this interface: **the service**, not the repository.
> In Java we write `ProductRepository`, put it next to the implementation, and the implementation says `implements ProductRepository`. Go flips it: **the consumer defines the interface**, and it lists only the methods it actually uses. Here, that's one.

【畫面】Switch to `internal/repository/product.go`; highlight line 28.

> And the repository? It has no idea anyone wants an interface. It just has a `List` method with the right signature, and that's enough. No `implements`. Go calls this implicit satisfaction.
> Episode 5 goes deeper. Tonight, remember one line: an interface is the consumer's shopping list, not the implementer's ID badge.

【畫面】Switch to `internal/handler/handler.go`; highlight lines 17–19.

> And the handler plays the same game one layer up: it declares `ProductLister` for the one method it needs from the service.
> Why bother? Because tomorrow we swap in-memory products for a real database, and the service won't change a single line. That's episode 2, and it's coming faster than my boss's next message.

## 8:00 Part three: chi and slog (the two tools we need tonight)

【畫面】`internal/handler/handler.go`; highlight lines 27–30.

> For routing we use chi. Why not a bigger framework? Because a chi handler is the standard library's `http.Handler`. It looks exactly like what you'll see in any Go codebase. You're learning Go, not a framework's private dialect.

> Now, middleware. In Spring you extend `OncePerRequestFilter`, override `doFilterInternal`, and remember to call `filterChain.doFilter`. In ASP.NET Core you write a class with `InvokeAsync` and a `RequestDelegate next`.
> And in Go?

```go
func(next http.Handler) http.Handler
```

> That's it. A function that takes a handler and returns a handler. **Functions wrapping functions.**
> Our logging middleware does three things: note the start time, call `next`, then log the method, path, status code and duration.

【畫面】`RequestLog`, lines 67–81; then circle `statusRecorder`, lines 56–64.

> Here's the one trap. In Java you can ask the servlet response for its status: `response.getStatus()`. Go's `ResponseWriter` has no such method. Once the status is written, you can't ask what it was.
> So we wrap it. `statusRecorder` peeks at `WriteHeader` on the way through, writes down the code, and passes it along untouched.
> Peeks. Doesn't change. Changing it is how you get your next incident.

【畫面】Terminal one: `curl localhost:8080/products`. Terminal two: one JSON log line appears.

> We log with `slog`, from the standard library. Structured logging, not to be confused with tonight, which is also a slog, but unstructured.
> Every field is a key and a value, and the output is JSON. Why structured? Because at 3 a.m. you don't want to eyeball a wall of text. You want to query it. Episode 11 pays that one back with interest.

【畫面】Zoom into the curl output: product names in Traditional Chinese, field `price_twd`.

> And yes, the product names are in Traditional Chinese and the prices are in Taiwan dollars. This shop is in Taipei. The handler sends `charset=utf-8`, JSON doesn't care, and neither does Go.

## 10:00 Proof: tests, then one real request

【畫面】`internal/handler/handler_test.go`; highlight lines 34–39.

> Claims without tests are just slides. Let's prove it.
> The default style for Go tests is table-driven: one table, one row per scenario, one loop runs them all.

```go
{"healthz", http.MethodGet, "/healthz", ..., http.StatusOK, -1},
{"products empty list returns []", ..., http.StatusOK, 0},
{"products service error", ..., http.StatusInternalServerError, -1},
{"products rejects POST", http.MethodPost, "/products", ..., http.StatusMethodNotAllowed, -1},
```

> If you write JUnit, this is `@ParameterizedTest` with a `@MethodSource`. If you write xUnit, it's `[Theory]` with `[InlineData]`. Go needs no annotation and no test library. `go test` ships with the language.
> And look: we never start a server. Spring has `MockMvc`; Go has `httptest` in the standard library. A fake request, a recorder, call the handler directly. It's almost suspiciously fast.

【畫面】Run `go test ./...`, all green. Then `go run ./cmd/api`, `curl /healthz`, `curl /products`.

> Green. Now the real thing. `go run`. [pause] Which is the command, and also my plan if this fails.
> `/healthz` says ok. `/products` returns three products.
> It's 11:58 p.m. Two minutes ahead of schedule. [pause] Yes, I made that number up.

## 11:30 Three-point wrap-up

> Let's wrap up.
> **One:** a Go project keeps entry points in `cmd/` and private code in `internal/`. A folder is a package, and a package is a boundary.
> **Two:** there's no DI container. Dependencies are created by hand in `main`, the compiler checks them, and you can read the whole wiring on one screen.
> **Three:** interfaces belong to the consumer and list only what it needs. And middleware is just a function wrapping a function.
>
> At 9 a.m. tomorrow, the shop opens.
> At 9:01, we redeploy a typo fix, and every product disappears, because they lived in memory.
> The boss will ask where the products went.
> Next episode: **the products need to survive a restart.**
> Ship it small, ship it tested. See you at the next incident.
