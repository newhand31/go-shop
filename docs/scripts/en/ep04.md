## 1:35 How we'd do it in Spring (and why Go won't play along)

【畫面】Split screen: left, a Spring `OncePerRequestFilter` subclass and a `@Bean FilterRegistrationBean`; right, an empty `middleware.go`.

> If you're coming from Java, this morning goes like so.
> You write a `Filter`, or a `OncePerRequestFilter` if you're feeling Spring-ish. You implement `doFilter`, you call `chain.doFilter(request, response)` to let the request through, and you register the thing as a bean with an `@Order` so it runs when you think it runs.
> Or you reach for Spring Security, and a filter chain you didn't write quietly decides things for you. C# folks, same story with `app.UseRateLimiter()` and `[EnableRateLimiting]`: it works, and you learn the framework's rules first. When does it run? Who decides the order? Answer: page 14 of the docs.

> So what does Go's standard library say? It says a handler is anything with a `ServeHTTP(w, r)` method.
> Want to add behavior? Write a function that takes a handler and returns a handler.
> That's the entire rule. There is no second rule.
> What does that tell us? It tells us a "filter" in Go isn't a framework concept. It's a function that returns a function. Let's go look.

## 3:20 Part one: a function that wraps a function

【畫面】`internal/handler/middleware.go`, the `RateLimit` signature and its last line.

```go
func RateLimit(limiter Limiter, logger *slog.Logger) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            ok, retryAfter := limiter.Allow(clientIP(r))
            if !ok {
                // write 429, then return: next is never called
                return
            }
            next.ServeHTTP(w, r)
        })
    }
}
```

> Look at the type: `func(http.Handler) http.Handler`. A handler goes in, a handler comes out.
> The handler we build can do one of three things. Run code before `next`. Run code after `next`. Or never call `next` at all.
> Our limiter does the third: when an IP is out of tokens, we write a 429 and `return`. **Not calling `next` is how you say no.** In Spring that's not calling `chain.doFilter`. In ASP.NET Core it's not awaiting `next`.

【畫面】Animation: an onion with three layers; the request goes in, the response comes out. Then the output of `TestChainOrder`: `first in, second in, second out, first out`.

> How do we stack them? `r.Use(a, b, c)` is shorthand for `a(b(c(router)))`. It's an onion. The request peels in from the outside layer to the router, and the response wraps back out the other way.
> We even wrote a test for it, `TestChainOrder`. Two middlewares that just log "in" and "out". The output: first in, second in, second out, first out. Going in and coming out are mirror images.
> Which is why order matters. Ours is: request log, panic recovery, rate limit, session.
> Why is the limiter before the session? Flip them, and a thousand-request flood **creates a thousand sessions**. The attacker gets free memory from us. Limit first, and the flood never reaches the session store.
> One more thing in that list: `Recover`. Go has a built-in called `panic`. It's the one time in this series I'll tell you: don't panic. Our `Recover` middleware catches it and returns the same `internal_error` shape from episode 3, and the panic message goes to the log, not to the customer.

## 5:50 Part two: rate limiting with a token bucket

【畫面】`internal/platform/ratelimit/ratelimit.go`, the `Allow` function.

> How do we count? The classic answer: a **token bucket**.
> Every IP gets a bucket. It holds 20 tokens, and gets 10 more every second. Each request takes one token. Empty bucket? 429, until a token shows up.
> A normal visitor makes five or six API calls per page. Their bucket never even gets low. A script firing a thousand per second? The first twenty pass. The rest are told to wait. Politely, we hope, as the script has been so far.

【畫面】The response headers for a 429, `Retry-After: 1`.

> We send `Retry-After`, so a well-behaved client knows when to come back instead of retrying immediately.
> Sure, this limiter is small. But it has three details worth stealing.
> One: **a mutex protects the map.** Many goroutines hit the same map at once, and Go will happily crash your process for that. One `sync.Mutex`, held for a few lines. The full concurrency story comes later in the series.
> Two: **idle buckets get swept.** Without that, a million IPs that each hit us once leave a million buckets in memory. A full bucket is the same as no bucket, so we delete those.
> Three: **the clock is injected.** The tests never call `time.Sleep`. They move a fake clock forward one second, and one second passes. Fast tests, and no flaky red builds because the CI machine was busy.

【畫面】`net.SplitHostPort(r.RemoteAddr)`, and next to it a crossed-out `X-Forwarded-For`.

> One trap: "which IP is this?" We use the connection's remote address and **ignore `X-Forwarded-For`**. That header is written by the client. If we trust it, the attacker sends a new fake IP every request, and we greet each one as a new customer.
> Sounds reasonable: trust the header, get the real IP. It isn't. That's leaving the house key under the doormat and calling it a smart lock. If you run behind a proxy you control, which hop to trust is a deployment decision, and we'll make it later in the series.

## 8:20 Part three: sessions, and `context`

【畫面】The `Session` middleware, circling `context.WithValue` and `SessionID(ctx)`.

> The limiter keeps the bad visitors out. Now let's recognize the good ones.
> The idea is plain. A new visitor gets a random id in a cookie. Next time they bring the cookie back, and we know who they are.
> The id is 32 hex characters from `crypto/rand`. **Not** `math/rand`. A guessable session id is a free account for whoever guesses. The cookie is `HttpOnly`, so JavaScript can't read it, and `SameSite=Lax`, so other sites can't quietly send requests with it.

> Fine, the middleware has the id. How does the handler three layers down get it? In Go, the answer is **`context`**.
> The middleware stores the id with `context.WithValue`, and later code reads it with `SessionID(ctx)`.
> Look at the key: it's a type we define and don't export. Another package can use the string "session" as a key all day, and it can't collide with ours. If you know `request.setAttribute` from servlets, or `HttpContext.Items` in C#, this is the same job, with a type guarding the door.

【畫面】The `SessionStore` interface: `Create`, `Exists`.

> One more thing. Where does the session live? Right now: in a map in memory. Restart the server and every session is gone. Run two servers and each has its own.
> That's on purpose. Notice that `SessionStore` has two methods, and that it's declared **in the handler package**, not next to the map. Why? Next episode will answer that.

## 10:20 The proof: one IP, a thousand requests

【畫面】`internal/handler/middleware_integration_test.go`, `TestFloodFromOneIPIsMostlyRejected`.

> Talking without proving is just a slide deck with extra steps. The incident was one IP, a thousand requests. So that's the test.
> Not a function call. A real HTTP server, real TCP, a thousand requests, one after another.
> We work out an upper bound: the bucket's capacity, plus whatever refilled while the test ran. The number of requests that pass must not exceed it.

【畫面】`go test -tags=integration -run Flood -v ./internal/handler` prints `ok=10 limited=990`.

> Out of a thousand, ten get through and nine hundred ninety get a 429. The exact numbers depend on your machine; the test checks the ceiling, not the digits.
> Then twenty goroutines at once. Same ceiling. That's the mutex earning its salary.
> And one more: a handler that panics on purpose. The connection doesn't drop. We get the same error shape as every other failure, and the panic message never leaves the server.

【畫面】Three terminal tabs: `curl -i /products` showing `Set-Cookie`; a 40-iteration loop printing 200s then 429s; one more request showing `Retry-After`.

> It's 11:40 a.m. The boss opens the log. Under that one IP: a wall of 429s.
> "So that customer is blocked?" he asks. I say: yes, and they got a note saying when to come back.

## 11:45 Three takeaways

> Let's wrap up.
> **One:** a Go middleware is `func(http.Handler) http.Handler`. Run before, run after, or never call `next`. Stacked, it's an onion: in and out in mirror order.
> **Two:** rate limit with a token bucket. Capacity sets the burst, refill sets the long-run rate. Protect the map with a mutex, sweep idle buckets, inject the clock, and never trust `X-Forwarded-For`.
> **Three:** a session is a random id in a cookie, and `context` is how a middleware hands a value to the code after it. Use your own key type.
>
> The boss's next message is a screenshot. A customer put three items in their cart. We redeployed. The cart is empty.
> Next episode: **the cart disappeared.**
> Ship it small, ship it tested. See you at the next incident.
