## 0:50 Time anchor

> It's 9:47 a.m., seven minutes after the boss's message, and one monitor has been held by an order nobody wants for sixty-one hours.
> Three things today: when an order stays unpaid too long, release it and put its stock back; wake a background goroutine on an interval with `time.Ticker` to do that; and give every round a deadline with `context.WithTimeout`, so a stuck round gets cancelled. Then we prove three things: an expired order is released, a paid one is left alone, and a round that runs out of time is cancelled.
> And we learn one thing: **Go's `context` replaces `CancellationToken`, and it brings one more thing with it: a deadline.**

## 1:40 How we'd do it in Spring (and why Go won't play along)

【畫面】Split screen: left, a Spring `@Scheduled(fixedDelay = 60_000)` method calling `releaseExpired()`. Below it, the ASP.NET Core version: a `BackgroundService` with `while (await timer.WaitForNextTickAsync(ct))`. Right, an empty `expiry.go`.

> Coming from Java, one annotation. `@Scheduled`, every minute, done. C# folks: a `BackgroundService` and a `PeriodicTimer`. Different words, same deal: **the framework runs the schedule.** It decides when to call you, who cancels you, whether shutdown waits for you. You only write what to do.
> Sure, that's convenient. But look at the case nobody thinks about: what if `releaseExpired()` gets stuck on a lock? A fixed-delay schedule waits for your method to finish before it counts the next delay. One stuck round, and every later round never comes, right when the stock most needs freeing. And neither framework puts a time limit on your method unless you remember to.
> Go has no `@Scheduled` and no `BackgroundService`. It hands you three parts: `time.Ticker`, `select`, `context`. You assemble them yourself.

> The good news is that it takes about twenty lines. The bad news is that two of them leak quietly if you forget them.

## 3:30 Part one: what does "unpaid too long" mean?

【畫面】`db/migrations/00006_add_order_expiry.sql`, circling `expired_at`; `db/queries/orders.sql`, circling `ClaimExpiredOrder`.

> First, define "unpaid too long". We already have `created_at`, and `paid_at` from episode 7. We add `expired_at`: once the stock is back on the shelf we stamp the order, so it can never be released twice.
> The condition: `paid_at IS NULL AND expired_at IS NULL AND created_at < cutoff`. Unpaid, not yet released, and old enough.

【畫面】`internal/repository/expiry.go`, `ReleaseOne`.

> Releasing one order does three things: add each line's quantity back to its product, stamp `expired_at`, commit. All in one transaction. Either the stock is back and the order is stamped, or nothing happened. We never get "stock returned, order still looks unpaid", which the next round would return again.
> Notice we release **one order per call**. Short transactions mean short locks, and the caller can stop between two orders when its time is up.
> The query ends with `FOR UPDATE SKIP LOCKED`, same trick as last episode. If a payment callback is updating that order right now, we skip it and look again next round. An order that is being paid doesn't get released under the customer's feet.
> Lock order matches checkout too: lines sorted by product id. Releasing and buying at the same moment can't deadlock.

> Honestly, releasing stock is simpler than taking it: adding needs no check, and nobody can add their way to a negative number. It's the only time in this series I've written database code and felt uneasy about how easy it was.
> The unease is justified: it only works if each order can be added back once. That's what the `expired_at` stamp is for.

## 5:45 Part two: `time.Ticker` plus `select`

【畫面】`internal/service/expiry.go`, `ExpiryJanitor.Run`.

```go
func (j *ExpiryJanitor) Run(ctx context.Context) {
    ticker := time.NewTicker(j.cfg.Interval)
    defer ticker.Stop()
    for {
        j.Sweep(ctx)
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
        }
    }
}
```

> That's the whole scheduler. `time.NewTicker` drops a value onto the channel `ticker.C` every interval. The `select` waits for two things: a tick, or `ctx` being cancelled. Cancelled? `return`. Same shape as last episode; only the work inside changed.
> `defer ticker.Stop()` is not optional. A ticker owns a timer, and a timer you never stop keeps running. It's Go's version of forgetting to `Dispose`.

> One more thing. The interval, the deadline, and even "what time is it" are fields in `ExpiryConfig`, not hard-coded. There's a `Now` field that defaults to `time.Now`. **The clock is a dependency you can inject.** In tests we don't wait fifteen minutes; we make "now" jump an hour ahead. Spring folks: this is the `Clock` you'd inject. C# folks: `TimeProvider`. Here it's a plain function field. No interface, no container.

> Why not just `time.Sleep(15 * time.Minute)` in the test?
> Because our CI would like to finish this year.

## 8:20 Part three: every round carries its own deadline

【畫面】`Sweep`, circling `context.WithTimeout`.

```go
roundCtx, cancel := context.WithTimeout(ctx, j.cfg.RoundTimeout)
defer cancel()
// ...
id, ok, err := j.store.ReleaseOne(roundCtx, cutoff)
```

> This is the real point of the episode. `context.WithTimeout` takes a context and returns a new one with a deadline. After thirty seconds it turns itself into "cancelled".
> C# folks, that looks like `new CancellationTokenSource(TimeSpan.FromSeconds(30))`. Close, with one difference: in Go the deadline **lives inside the context**. It isn't a second thing you have to remember to pass along. `ReleaseOne` hands the context to the database driver, and while the driver waits for the database, it watches the deadline too. When time is up, the call returns by itself with `context.DeadlineExceeded`.
> In `Sweep` we sort that error into three cases. `DeadlineExceeded` while the outer `ctx` is still fine: this round ran out of time; log a warning and wait for the next tick. Any other error: log it and end the round. The outer `ctx` cancelled: that's shutdown, not a failure, so stay quiet.
> `defer cancel()` is the second one that leaks quietly. `WithTimeout` holds a timer, and if you never call `cancel`, you wait for the full deadline to release it.

> Our janitor is firm with stuck colleagues: thirty seconds, then it moves on. The stuck round is cut off, the next one starts clean, and no single round can freeze the schedule.

【畫面】`cmd/api/main.go`: both workers share one `workerCtx`; one `defer` cancels it and waits for both.

> Starting it works as in the last episode: whoever starts it stops it. A context says "stop", a channel says "I have stopped". Now there are two goroutines, so one shared context and one `defer`.

## 10:00 The proof: three things

【畫面】`go test ./internal/service -run Expiry -v`, then `go test -tags=integration ./internal/repository -run Expiry -v`, all green.

> One: an expired order is released. We place an order for two products, including the last monitor. Then we make the clock jump an hour ahead and sweep once. Result: both products are back to their original stock, the monitor is back to one, and `expired_at` is set. Sweep again: zero released, and the stock is not added a second time.
> Two: a paid order is left alone. Same order, but we record a payment with episode 7's `Record`, jump the clock an hour, sweep. Result: zero released, and the stock stays decremented. Somebody who paid doesn't lose their order to our janitor.
> A counter-example: an unpaid order that is only seconds old, swept with the real clock, isn't touched either. We don't release "unpaid"; we release "unpaid and old enough".

> Three: a round that runs out of time is cancelled. This test uses a fake store that, when called, waits forever for its context. We set the round timeout to twenty milliseconds. Result: `Sweep` returns when the deadline hits, and the fake store saw `DeadlineExceeded`. The test has a two-second safety net, so a missing deadline shows up as a failure, not a hang.
> Take out the `WithTimeout` line and this test fails at the two-second net. That's how we know the line does something.

> Plus the usual: `Run` returns after its context is cancelled. Same test as last episode.

## 11:45 Three takeaways

> Let's wrap up.
> **One**, Go has no `@Scheduled` and no `BackgroundService`. A schedule is `time.Ticker` plus `select`: twenty lines, and they're yours.
> **Two**, every round needs a deadline. `context.WithTimeout` cancels a stuck round, so it can't drag every later round down with it.
> **Three**, `context` replaces `CancellationToken` and carries a deadline too. `defer cancel()` and `defer ticker.Stop()` are not optional.
>
> The boss's next message: "It's Singles' Day, and the database says it's out of connections."
> Ship it small, ship it tested. See you at the next incident.

## Appendix B: open questions

- Laugh timestamps are estimates; re-time them against the real voice-over length before recording.
- Payment vs release race: if a payment callback and the release hit the same order at once, `SKIP LOCKED` makes the release skip. But if the order was already released and a payment callback for it arrives later, `MarkOrderPaid` still marks it paid while its stock is already back. Paying after expiry is not handled in this episode and has no test.
- Releasing only returns stock and stamps the order. No customer notification, and no "expired" status shown in the API.
- Defaults: sweep every minute, release after 15 minutes unpaid, 30-second round budget. There are no environment variables to change them.
- Running the janitor on several API instances at once is safe (`SKIP LOCKED`), but there is no multi-instance test.
- The round-timeout test uses a fake store; no test makes a real database call stall on a lock.
