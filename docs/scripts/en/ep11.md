# Episode 11 | 2 a.m., and nobody can say which step was slow (voice-over draft v0, English channel)

- Target length: about 11 minutes (about 1,450 spoken words plus screen-only beats and code on screen; re-time after recording)
- The one main concept: **the context carries the trace.** The first thing a request does is open a span and put it in `context.Context`; every layer below reads the same trace id from it. Logs get the id from a `slog.Handler` that reads the context, and metrics are labelled by route pattern. The comparison that matters: Java's MDC and C#'s `Activity.Current` pass the id around invisibly (thread-local, async-local); Go has no ambient state, so you pass `ctx` by hand. That's the chore, and it's also why the id never quietly vanishes halfway

## 1:40 How we'd do it in Spring (and why Go won't play along)

【畫面】Split screen: left, Spring Boot with Micrometer Tracing and Actuator, `/actuator/prometheus` appearing by itself, a `traceId` in the MDC; below it, C#: `AddApplicationInsightsTelemetry()` and an `ILogger` that picks up `TraceId`. Right, an empty `main.go`.

> Coming from Java: add a starter, Micrometer opens the spans, puts `traceId` in the MDC, and your logs have it. C# folks: `Activity.Current` travels in the background and `ILogger` reads it.
> Lovely. And both do it the same way: **ambient state.** The MDC is a `ThreadLocal`. `Activity.Current` is an `AsyncLocal`. You never pass anything; it's just there.
> Which is the problem with things that are just there: they're gone when you aren't looking. The MDC is a sticky note on one thread's desk. Hand the job to a thread pool and the note stays on the old desk. **Spring's fix is a decorator whose entire job is photocopying sticky notes between desks.**
> Go has none of that. No `ThreadLocal`, and a goroutine has no "current span". If you want it to travel, you put it in the `context.Context` and pass it down as the first parameter. Pass it, it's there. Don't, it's not there, and it never disappears halfway through without you noticing. Context is everything. Literally; it's the first argument.

> So in Go we wire it ourselves. Not a starter: about a dozen lines in `main.go`. That's this episode's cost, and its upside: you can see where every wire goes.

## 3:30 Part one: traces, open a span as the request arrives

【畫面】`cmd/api/main.go`, circle `NewTracerProvider` (line 104) and `otelhttp.NewHandler` (line 219).

```go
tp, err := telemetry.NewTracerProvider(os.Getenv("OTEL_TRACES_EXPORTER"), os.Stderr)
otel.SetTracerProvider(tp)
...
shop := otelhttp.NewHandler(handler.WithPaymentCallback(...), "shop", otelhttp.WithTracerProvider(tp))
```

> OpenTelemetry comes in two halves in Go. The API, `otel` and `trace`, is what your code uses to open spans. The SDK, `sdktrace`, decides where spans go. In `main` we build a tracer provider and install it globally.
> Then we wrap the whole server in `otelhttp.NewHandler`, the outermost layer. Every request arrives, it opens a span and puts it in the request's context. By the time `RequestLog`, a handler, or a service runs, the span is already in `ctx`.
> Do we need an external collector? No. `OTEL_TRACES_EXPORTER` defaults to `none`: spans are still created and trace ids still exist, they're just not sent anywhere. Set it to `stdout` and spans become JSON on stderr. A real collector later means changing one file, `telemetry`, not the callers. **It's like holding a full meeting in an empty room: agenda, minutes, meeting number, and nobody came.** But the point isn't who came; it's that the id exists, so the next part can use it.

【畫面】`internal/service/order.go`, line 78.

```go
placeCtx, span := otel.Tracer("go-shop/service").Start(ctx, "order.place", ...)
placed, err := s.store.Place(placeCtx, lines)
```

> We also open one child span by hand: `order.place`, around the part that actually talks to PostgreSQL. It starts from the context it was handed, so it hangs under the request span on its own. Next time checkout is slow, the trace shows whether the time went into the transaction or somewhere else.
> Notice the name: `placeCtx`, not `ctx`. We don't overwrite the original, because the cart-cleanup warning further down should log with the request's context, not with a span that has already ended.

> Sure, today's trace has two levels: the request, and the order. The database call and Redis don't have spans of their own. But two levels beat twelve hundred sticky notes. We note the gap in the appendix.

## 5:45 Part two: logs carry the trace id, one `slog.Handler` is enough

【畫面】`internal/platform/telemetry/slog.go`, circle `Handle` (line 20) and `WithAttrs` (line 29).

```go
func (h logHandler) Handle(ctx context.Context, r slog.Record) error {
    if sc := trace.SpanContextFromContext(ctx); sc.IsValid() {
        r.AddAttrs(slog.String("trace_id", ...), slog.String("span_id", ...))
    }
    return h.inner.Handle(ctx, r)
}
```

> Every request has a trace id now. How does a log line find out? Through `slog`'s handler, which is an interface. We write one that wraps the usual JSON handler. Each record passes through us; we look in `ctx` for a span, and if there is one, add two fields. Take one handler, return one: the same shape as a middleware.
> Two traps. First, you must call `InfoContext`, not `Info`. Plain `logger.Info` has no context, so we have nothing to read, and the line goes out quietly without an id. That's why `RequestLog`, `Recover`, `writeError` (where the real cause of a failure is logged) and the payment callback now log with the request's context.
> The second one is nastier. `logger.With("order", 7)` calls the handler's `WithAttrs`, which must return a new handler. If you just forward the call to the inner handler, what comes back is **unwrapped**: every line from that logger has no trace id. **This bug throws no error and turns no test red. It just goes quiet, exactly like the 2 a.m. complaint.** So `WithAttrs` and `WithGroup` must return our own type, and there are tests standing guard.

> Our logs finally have names. Within one request, every line logged with its context shares a `trace_id`: the request line, the real cause of an error response, the checkout warning, the payment callback. Take the id from the complaint, search, and twelve hundred lines become that one request's few.

## 7:30 Part three: metrics, label by route pattern, not by path

【畫面】`internal/handler/observe.go` (`Instrument`, from line 23); a browser on `/metrics`.

```text
http_requests_total{method="GET",route="/products/{id}",status="200"} 2
http_request_duration_seconds_count{method="GET",route="/products/{id}"} 2
```

> Traces and logs answer "what happened to this one request?" The boss asks about all of them: how many, how slow, how many failed. That's metrics. With Prometheus's Go client we add two: a request counter, and a latency histogram. `GET /metrics` prints them as text, and Prometheus comes by on a schedule to read it.
> The one line in this episode that bites: **the label.** If the label is the raw path, `/products/1`, `/products/2`, every product id becomes a new time series. Worse, scanners never get tired. A scanner can invent infinite paths for us: `/wp-admin`, `/.env`, a random string. The metrics store has to remember every one. We planned to track a hundred routes; a scanner handed us a million. We planned to pay for monitoring; we ended up paying for a scanner's imagination.
> So the label is chi's **route pattern**, `/products/{id}`. A million products, still one series. Anything no route claims is `unmatched`, whether it's a scanner or a typo. (In the real wiring chi's `Mount` labels those requests `/*`; `routeLabel` folds that into `unmatched` too.)
> One detail: the pattern has to be read **after** the request has run, because chi only knows which route matched once routing is done. So `Instrument` calls `next` first, then reads. It sits **in front of** the rate limiter so a 429 is counted, and a `defer` records a panic as a 500 before `Recover` answers. A 429 never reached routing, so it is labelled `unmatched`.

## 9:00 Where does all this run?

【畫面】`cmd/api/main.go` from line 220: `mux.Handle("GET /metrics", ...)`; a terminal after `$env:OTEL_TRACES_EXPORTER="stdout"`, span JSON scrolling by.

> You may be wondering: where's Jaeger? Grafana? The collector?
> We have none of them. **Tonight's observability platform is called stderr.** That's on purpose: first prove the id reaches the log and the metrics come out; then decide where to ship them. Wiring is a dozen lines in `main`. Where it goes is a decision for after launch.
> `/metrics` sits beside the shop, outside the rate limiter and the session, because Prometheus isn't a visitor. In a real deployment that path belongs on an internal port, not out in the open with the shop. It's in the appendix.

> Last thing, shutdown: spans are sent in batches, so whatever is still in the queue has to be flushed with `Shutdown` before the program ends. A `defer` at the top of `main` does that. But the way we shut the server down is still crude: on an interrupt we just close it. That's next episode.

## 10:00 Proof: two things

【畫面】`go test ./internal/handler -run "TraceID|Metrics" -v`, then `go test ./internal/platform/telemetry ./internal/service -run "Log|Span|Exporter|Observe" -v`, all green.

> One: the log has the trace id. The test builds the chain in the same order as `main`: `otelhttp` outermost, then the router with `RequestLog` and `Instrument`. Send a request, parse the log line: its `trace_id` equals the one the handler itself sees in `ctx`, and there's a `span_id` too.
> A second group of tests guards the handler: a context with a span gets the id, `context.Background()` doesn't, and the id survives `logger.With` and `WithGroup`. If someone breaks the quiet bug we just described, those go red.
> Two: `/metrics` shows the new series. Hit `/products/{id}` twice and a nonexistent path once, then read `/metrics`: `http_requests_total` for the route says two, `unmatched` says one 404, and the output contains **no** raw path like `/products/1`. The test uses the same wiring as `main` (the `Mount` inside `WithPaymentCallback`), and one more test shows that a rate-limited 429 and a handler panic's 500 both reach the metrics.
> One more: a service test proves `order.place` is a child of the request span, and carries an error status when the order fails.

## 11:45 Three takeaways

> Let's wrap up.
> **One**, the context carries the trace: open a span when the request arrives, put it in `ctx`, pass it down as the first parameter. Go has no ambient state, so it doesn't silently drop it halfway either.
> **Two**, logs need the id: a `slog.Handler` copies the trace id out of `ctx`, and `WithAttrs` and `WithGroup` must return the wrapped handler.
> **Three**, label metrics by route pattern, never by raw path, or every path becomes a time series.
>
> The boss's next message: "We just deployed, and people say checkout drops the connection when they press the button."
> Ship it small, ship it tested. See you at the next incident.

## Appendix B: open questions

- Laugh timestamps are estimates; re-time them against the real voice-over length before recording.
- `AlwaysSample`: every request gets a real trace id, which is why every log line has one. Real traffic would sample, but the id would still stay on the log.
- No propagator is configured, so `otelhttp` does not read an incoming `traceparent` header: every request starts a new trace. Enough for one service; a caller or callee service would need one.
- Every request's root span is called `shop` (chi has no route pattern outside `otelhttp`); to see which route is slow, read the metrics, not the span name.
- A trace has two levels, the request and `order.place`. pgx and Redis calls have no spans of their own.
- Only log calls made with the `*Context` methods carry an id. This episode changed `RequestLog`, `Recover`, `writeError`, the payment callback (handler and service) and the cart-cleanup warning in checkout. The log line `writeJSON` writes when a response fails, and 404/405, carry none. Background goroutines (mail, janitor, flash-sale workers) belong to no request and log without one.
- `/metrics` shares the shop's port and has no authentication. Histogram buckets are guesses, not calibrated on real traffic. Requests to `/metrics` itself are not counted.
- New configuration: `OTEL_TRACES_EXPORTER` (`none` by default, or `stdout`; any other value fails at startup). No new config files.
- The span `Shutdown` is a `defer` near the top of `run`, so it runs last; on an interrupt `srv.Close()` still cuts connections, and the full shutdown order is episode 12.
- New dependencies: the OpenTelemetry SDK and stdout exporter, `otelhttp`, the Prometheus client. Tests use `tracetest` (part of the SDK).
- The sign-off is the fixed line from §6.1.
- The next-episode teaser only states the symptom (the connection drops during a deploy), not the fix.
