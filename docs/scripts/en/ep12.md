# Episode 12 | Every deploy throws a customer out (voice-over draft v0, English channel)

- Target length: about 11 minutes (about 1,350 spoken words plus screen-only beats and code on screen; re-time after recording)
- The one main concept: **shutdown is a procedure you design.** On the stop signal: stop accepting requests, let the running ones finish, stop the background goroutines, close the database last. The comparison that matters: Spring Boot's graceful shutdown and ASP.NET Core's `IHostApplicationLifetime` sit inside a host that orders all this for you; Go's `http.Server` hands you one part, `Shutdown`, and `main` is the host. The deployment half (multi-stage Dockerfile, `scratch`) rides along because a single static binary is what makes it possible

## 1:40 How we'd do it in Spring (and why Go won't play along)

【畫面】Left: Spring Boot, `server.shutdown=graceful` and `spring.lifecycle.timeout-per-shutdown-phase`; below it ASP.NET Core, `IHostApplicationLifetime.ApplicationStopping`. Right: our `main.go` ending in a single `srv.Close()`.

> Coming from Java: in Spring Boot you set `server.shutdown=graceful`, and the embedded server stops taking new requests and waits for running ones, with a timeout you can tune. Fun fact: the default is immediate. So we're not the only shop that has thrown a customer out. C# folks: the generic host does the same on SIGTERM, with a shutdown timeout, and `IHostApplicationLifetime` lets you hook in before it happens.
> What they have in common: **the framework chose the order.** You hang a few callbacks on a sequence somebody else wrote.
> Go's standard library has no host and no sequence. `http.Server` gives you two parts: `Close`, which cuts every connection now, and `Shutdown`, which closes the door and waits for the people inside. Which one you call, when, and whether the background goroutines go before or after, is nobody's decision but yours, because `main` is the host.
> Annoying? Sure. And **last episode's single `srv.Close()` is the wrong part, picked with confidence.**

## 3:30 Part one: the signal, and what Docker actually sends

【畫面】`cmd/api/main.go`, line 102.

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
```

> First question: how do we even know it's time to stop? The operating system sends a signal. Ctrl+C in a terminal is `os.Interrupt`. But `docker stop`, and any orchestrator, sends `SIGTERM`. We only listened for Ctrl+C. So on a laptop it always worked. In a container the signal arrived, nobody signed for it, ten seconds later Docker sent `SIGKILL`, which cannot be caught, and the process simply vanished.
> `signal.NotifyContext` hands you a `ctx` that is cancelled when the signal lands. From here the whole shutdown waits on `ctx.Done()`.
> One thing to hold on to: **in this program `ctx` means "stop taking new requests". It does not mean "stop everything".** Part three needs that.

## 4:30 Part two: `Shutdown`, and an error value that lies

【畫面】`internal/platform/lifecycle/lifecycle.go`, `Serve` from line 21.

```go
go func() { serveErr <- srv.Serve(ln) }()
select {
case err := <-serveErr:
    return fmt.Errorf("serve: %w", err)
case <-ctx.Done():
}
shutdownCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), grace)
defer cancel()
if err := srv.Shutdown(shutdownCtx); err != nil {
    _ = srv.Close() // out of time: cut what is left
    ...
}
```

> `srv.Shutdown(ctx)` closes the listening port right away, so no new connection gets in; lets the requests already inside finish; and returns when the last one is done. The `ctx` is "how long are you willing to wait". When it runs out you get an error, and we use `Close` on whatever is left.
> Two details. First: you can't hand `Shutdown` the signal context, because it's already cancelled and `Shutdown` would give up on its first line. So we take a clean one with `context.WithoutCancel` and add our own countdown. Second, `defer cancel()`: `defer` is the one thing in this program that reliably cleans up after itself. [pause] I'm working on it.
> Now the lie. The moment you call `Shutdown`, `srv.Serve` returns `http.ErrServerClosed` **immediately**. It means "I started closing", not "I finished closing". If your `main` sees that error and exits, the running requests are cut off right in front of you. **It's a restaurant that flips the sign to "Closed" and the owner goes home, while six tables are still waiting on the kitchen.** So we wait for `Shutdown` to return, not for `Serve`.

> Sure, the wait needs a ceiling. We set 25 seconds, adjustable with `SHUTDOWN_GRACE_SECONDS`. Why 25? Next part.

## 5:45 Part three: order matters, background goroutines go after the server

【畫面】`cmd/api/shutdown.go`, `serveThenStop`; and `main.go` from line 174.

```go
workers := lifecycle.NewGroup()
defer workers.Stop()
workers.Go(dispatcher.Run)
workers.Go(janitor.Run)
workers.Go(sale.Run)
...
err = serveThenStop(ctx, srv, ln, grace, workers)
```

> We have three background goroutines: the mailer, the janitor for expired orders, and the flash-sale workers. Last episode their context grew out of the signal context, so when the signal came they got "stop" at the same moment as the server.
> Picture one flash-sale worker. It's writing buyer A's order. Buyer B's request was accepted and is waiting in the queue. The signal arrives. If the worker stops now, B's request is alive, its connection is open, and nobody will ever serve it. B gets a 503. **The sign flips to "Closed" and the cook clocks out in the same second; the customer's dinner sits on the pass.**
> So the order is: drain the server first, then stop the workers. We wrote a very small `lifecycle.Group`. Its context is not derived from the signal; only `Stop` cancels it, and `Stop` waits until every goroutine has returned. `serveThenStop` is two lines: `Serve`, then `workers.Stop()`.
> Now look at `main`'s `defer`s; they run in reverse. After `serveThenStop` returns, the deferred `workers.Stop()` runs (already stopped, calling it again is harmless), then Redis closes, then the connection pool, and last the spans that haven't been sent are flushed. **Whoever uses something closes after it.**
> One more number. The server drains for up to 25 seconds, spans flush for up to 5, so in compose `stop_grace_period` is 40 seconds. Docker's default is 10. Leave it, and our graceful shutdown gets `SIGKILL`ed halfway.

## 7:30 Part four: the Dockerfile, multi-stage, `scratch`

【畫面】`Dockerfile`.

```dockerfile
FROM golang:${GO_VERSION}-alpine AS build
...
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/api ./cmd/api

FROM scratch
COPY --from=build /out/api /api
USER 65532:65532
ENTRYPOINT ["/api"]
```

> Shutdown works; let's put it in a container. Java folks: your image carries a JRE. C# folks: a .NET runtime. Plus an operating system's worth of files. Go builds a static binary. There's no runtime to bring, and even the database migrations are baked in with `embed`. So the final image can be `scratch`: **genuinely empty.**
> Two stages: the first has the whole Go toolchain and compiles; the second receives only the compiled file. The toolchain, the source, the module cache, none of it ships. `go.mod` and `go.sum` are copied first so "download dependencies" is its own cached layer. Edit one line of code and we don't re-download the world.
> `CGO_ENABLED=0` is the most important line here. Without it the binary may link dynamically against libc, and `scratch` has no libc: the container starts and says "file not found", about a file that is right there. **How empty is `scratch`? No shell. No `ls`. No `curl`. Something's wrong in there and you want to look around? Look at what, the binary?**

---

## 9:00 The decisions, and why

【畫面】The last lines of `Dockerfile`; the `api` service in `docker-compose.yml`.

> A few deliberate choices.
> One: `ENTRYPOINT` in **array form**. This is the line that matters most for shutdown. Written as `ENTRYPOINT /api`, Docker wraps it in `/bin/sh -c`; PID 1 is the shell, `SIGTERM` goes to the shell, and the shell does not necessarily pass it on. **The signal was delivered. To the front desk, not the chef.** The array form makes our program PID 1, so it receives the signal itself.
> Two: `USER 65532`, a plain number. `scratch` has no `/etc/passwd`, nothing to look a name up in, and we don't want root anyway.
> Three: **no `HEALTHCHECK`.** A health check runs a command, and `scratch` has nothing to run it with. It isn't an oversight; it's a trade: let the platform probe `GET /healthz`.
> Four: `.dockerignore` keeps `.git`, docs and scripts out of the build context, so we don't copy the project's whole history into the build.
> Last: the `api` service in compose sits behind an `app` profile. A plain `docker compose up` is still databases only; to run the shop, add `--profile app`.

## 10:00 Proof: a running request finishes, a queued buyer isn't dropped

【畫面】`go test ./internal/platform/lifecycle ./cmd/api -v`, all green.

> Two things to prove. One: a running request really finishes. The test starts a server whose handler waits on a channel. A request comes in; we cancel the signal context; `Serve` has **not** returned. Release the channel, the client receives the full response, and only then does `Serve` return, with `nil`. Other tests show that once shutdown starts new connections are refused, and that when the time runs out the connection is cut and the error wraps `context.DeadlineExceeded`.
> Two: a queued flash-sale buyer isn't dropped. This test uses the same calls `main` does: a `lifecycle.Group` and `serveThenStop`. One worker. Buyer A is stuck in the database, buyer B waits in the queue. The signal arrives, we release A, and **both get a 201.** If you swap the two lines inside `serveThenStop`, this test goes red.
> One more test just reads the Dockerfile as text: the last stage must be `FROM scratch`, `ENTRYPOINT` must be the array form, the build must set `CGO_ENABLED=0`. **It does not build an image.** It guards three lines; it doesn't prove the image boots.

## 11:45 Three takeaways

> Let's wrap up.
> **One**, shutdown is a procedure: stop accepting requests, let running ones finish, stop the background goroutines, close the database last. `Serve` returning `ErrServerClosed` only means "started closing".
> **Two**, background goroutines must not take their context from the signal. They wait until the server has drained before they're allowed to stop.
> **Three**, the container: multi-stage build, `CGO_ENABLED=0`, `scratch` as the last stage, and `ENTRYPOINT` in array form so your program actually receives `SIGTERM`.
>

## Appendix B: open questions

- Laugh timestamps are estimates; re-time them against the real voice-over length before recording. The script is about 1,350 spoken words, roughly 10–11 minutes.
- Re-check the `main.go`, `lifecycle.go` and `shutdown.go` line numbers against the final sha before recording.
- Image size: the voice-over quotes no number. While drafting I ran `docker build` once locally: `docker image ls` showed about 19 MB; after `docker compose --profile app up`, `/healthz` returned 200, and after `docker compose stop api` the log showed `stop signal received: requests drained, workers stopped` with exit code 0. That is one manual observation, not an automated test; re-run it before recording if it goes on screen.
- There is no `HEALTHCHECK`; probing is left to the platform hitting `GET /healthz`. `/healthz` keeps returning 200 until the listener closes, so there's no "draining" readiness signal; behind a load balancer you'd fail the readiness probe first and wait a few seconds before acting on the signal. Not done here.
- `lifecycle.Group.Stop` has no timeout: a goroutine that ignores its context makes `Stop` wait, and the platform's `SIGKILL` ends it.
- `http.Server` has no `ReadHeaderTimeout` or similar: a slow connection can occupy the drain time. A hardening topic, not this episode's.
- `Shutdown` does not track hijacked connections such as WebSockets; the shop has none.
- 25 s (`SHUTDOWN_GRACE_SECONDS`) plus up to 5 s for the span flush is why compose says `stop_grace_period: 40s`; worker stop time comes on top.
- Rolling deploys (two versions alive for a few seconds) and migration/schema compatibility are not discussed.
- A flash-sale request cut off when the grace expires: the connection drops, and `Buy` returns the reservation if no worker has claimed the job; a claimed one finishes. No new test for this; it relies on episode 10.
- New configuration: `SHUTDOWN_GRACE_SECONDS` (default 25). No new dependencies.
