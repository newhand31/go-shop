# Episode 7 | We took the same payment twice (voice-over draft v0, English channel)

- Target length: 11–13 minutes (about 1,600 spoken words plus screen-only beats and code on screen)
- The one main concept: **the idempotency key**: ECPay resends its payment callback, so "record each payment once" has to be guaranteed by a database unique key (`UNIQUE` plus `ON CONFLICT DO NOTHING`). Verifying the signature (`crypto/sha256`, `net/url`) comes first, written by hand with the standard library only

## 0:50 Time anchor

> It's 9:20 p.m., eight minutes after finance's message, and our revenue sheet contains NT$1,290 that never existed.
> Three things today: write the signature check ourselves, so we know the call really came from ECPay; use one unique key so a resent callback is booked once; and send the same callback ten times at once to prove it.
> And we learn one thing: **in Go, nobody dedupes for you. You store the idempotency key yourself, and you store it in the database.**

---

## 1:40 How we'd do it in Spring (and why Go won't play along)

【畫面】Split screen: left, a Spring `@PostMapping("/ecpay/callback")` with `if (!paymentRepository.existsByTradeNo(tradeNo)) { paymentRepository.save(...); }`. Right, an empty `payments.go`.

> Coming from Java, you write the obvious thing. Receive the callback. Ask the repository, `existsByTradeNo`. If it says no, `save`. C# folks: `AnyAsync`, then `Add`, then `SaveChanges`. Looks reasonable.
> Look at the gap between those two lines. ECPay resends 0.2 seconds later. Two requests reach the `exists` check. Each one sees "never booked". Each one saves. Nothing stood between the question and the answer. You've seen this shape before, in episode 6. It has a name: a race.
> Sure, you can add a de-duplication filter, or pull in a library. But neither Spring nor ASP.NET Core ships "handle this request only once". Somebody still has to write the filter, store the state, and remember that two requests can arrive together. Who wants to own that at 9 p.m. on a Friday?

> Go doesn't ship it either. So the star of this episode isn't code. It's one line of SQL.

## 3:30 Part one: is it really ECPay? (the signature, by hand)

【畫面】`internal/payment/ecpay/ecpay.go`, `CheckMacValue`.

> Before we dedupe anything, a more basic question. **Did ECPay really make this call?** The callback URL is public. Anyone can post "order forty-two is paid" to it.
> ECPay's answer is a signature called `CheckMacValue`. The rules are in its documentation, and we follow them with nothing but the standard library. Six steps.
> One: sort the fields by name, ignoring case. Two: join them as `k=v&k=v`, with `HashKey=` in front and `HashIV=` at the back. Three: URL-encode the whole string. Four: lower-case it. Five: put back `!`, `*`, `(` and `)`, because .NET's encoder leaves them alone and Go's doesn't. Six: SHA-256, hex, upper-case.
> Steps three to five are where everyone trips. Forget one parenthesis and the whole signature mismatches, and the only error you get is "mismatch".

【畫面】`ecpay_test.go`, `TestCheckMacValue_GoldenVectors`.

> How do we know we got it right? The expected values in this test were computed by a different program, in a different language, from the same six steps. They include spaces, parentheses, stars, an apostrophe, and mixed-case field names. Most of the rules people get wrong are in there (`~` and non-ASCII item names aren't yet; add before recording). Checking your own output against your own output isn't a test. It's a pep talk.

【畫面】`Verify`, circling `subtle.ConstantTimeCompare`.

> Two details. First: verify, and only then read the fields. An unsigned body is attacker input. Second: compare signatures with `ConstantTimeCompare`, so the response time doesn't leak how many leading characters were right.
> The tests try every way to cheat: amount rewritten after signing, order number changed by one digit, an extra field, no signature, garbage as a signature, a different key. Every one comes back `ErrBadSignature`.

## 5:45 Part two: the idempotency key is one line of schema

【畫面】`db/migrations/00004_add_payments.sql`, circling `trade_no text NOT NULL UNIQUE`.

> Signature passes. Now the actual incident.
> ECPay gives every payment a transaction number, `TradeNo`. A resent callback carries the same one. That's an idempotency key: **the same event always arrives under the same name.** We store it in the `payments` table and declare it `UNIQUE`.
> Notice what we didn't write: "check first". We hand the guarantee "at most one" to the database. Two requests arrive together; the database lets one write first, and the other finds the key taken.

【畫面】`db/queries/payments.sql`: `ON CONFLICT (trade_no) DO NOTHING`.

> What should happen when the key is taken? If we return an error, ECPay decides we never got the message and keeps resending, and we've built ourselves a loop. So: `ON CONFLICT DO NOTHING`. A collision isn't an error. It's "zero rows affected".

【畫面】`internal/repository/payments.go`, `Record`.

```go
n, err := q.InsertPayment(ctx, ...)
// ...
case n == 0:
    return false, nil // already recorded; the first call did the work
```

> `Record` returns "did this call actually book it?" Zero rows means "already booked": `false`, not an error. The service turns that into one log line: "duplicate callback ignored". To ECPay, the first delivery and the tenth get the same answer: `1|OK`.
> And the transaction from episode 6 shows up again. Booking the payment and marking the order paid happen in one transaction. If the amount doesn't match, the whole thing rolls back, including the payment row.

## 8:20 Part three: two kinds of "no"

【畫面】`internal/handler/payment.go`, the `switch` in `ECPayCallback`.

> One last detail: the reply. ECPay recognises exactly one string, `1|OK`. Anything else, it resends. We can use that.
> Bad signature, wrong amount, unknown order: resending won't fix any of those, so we answer 400 (ECPay will still retry a few times by its own rules, but every retry gets the same answer, so one log line is enough). Our own problem, say the database is down: answer 500, and **do not** say `1|OK`, because we didn't book it and we want ECPay to try again. `1|OK` means "I have it", not "I saw it".
> And a notification that a payment failed? We also answer `1|OK` and just log it. Resending it won't change the outcome.

【畫面】`WithPaymentCallback`: an outer router with `/payments/ecpay/callback`, everything else handed to the existing API.

> This route sits outside the rate limiter and the session middleware. The caller is ECPay's server, not a visitor. It has no cookie, and it shouldn't be throttled like an IP firing a thousand requests a second. Its proof of identity is the signature.

---

## 10:00 The proof: one callback, ten at once

【畫面】`go test -tags=integration ./internal/repository -run Payments -v`, all green.

> First the test. One signed callback, ten goroutines waiting on the same starting gun, all firing together. Result: all ten get `1|OK`, the `payments` table has one row, the order is paid.
> Then the counter-examples. A different `TradeNo` is a different payment and gets its own row; only a repeat is dropped. A forged signature, a wrong amount, an unknown order: all 400, and nothing left behind in the database.
> One more. We bypass the service and insert the same `TradeNo` twice straight into the database. The second insert is rejected by the database itself. The key doesn't depend on our code behaving.

> And I did one more thing. I deleted the `ON CONFLICT` line and ran it again. The test went red: some of the ten got a 500. A test earns its place by failing when the fix is removed.

> It's 9:55 p.m. Finance writes back: "Order forty-two. One payment. It matches."
> I say: "That was always the plan."

---

## 11:45 Three takeaways

> Let's wrap up.
> **One**, the callback is a public URL: verify the signature, then read the fields. Writing it yourself is six steps, but take the expected values from a different implementation.
> **Two**, nobody dedupes for you. Store the idempotency key yourself, in the database, with `UNIQUE` and `ON CONFLICT DO NOTHING`, not "check, then write".
> **Three**, answer precisely. Your fault: no `1|OK`. A repeat: `1|OK`.
>
> The boss's next message: "A customer paid and says he never heard back from us."
> Ship it small, ship it tested. See you at the next incident.

## Appendix B: open questions

- The API refuses to start without the three `ECPAY_*` variables; the demo uses `ECPAY_SANDBOX=1`. This is deliberate: an endpoint verified with a published key would accept anyone's forged "paid".
- No "create payment" code: this episode covers only the callback side. Tests play ECPay's part with ECPay's published sandbox credentials and a `Sign` helper. Redirecting to ECPay's checkout page comes later; do not imply the shop can take money yet.
- `MerchantTradeNo` is `GS` plus the order id (ECPay allows at most 20 letters and digits). Paying the same order again would need a fresh number in practice; not handled.
- Two payments with different `TradeNo` for one order (genuinely paid twice) are each recorded and the order stays paid. Refunds and manual reconciliation are out of scope.
- `paid_at` uses `COALESCE`, so a repeat never overwrites the first timestamp.
- The expected signature values come from an independent implementation in another language, not from an example copied out of ECPay's docs. Before recording, it is worth one real call against ECPay's sandbox as a cross-check.
- Checkout (`POST /checkout`) is still not idempotent; this episode does not touch it.
- The sign-off is the fixed line from §6.1.
