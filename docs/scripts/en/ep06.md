## 1:40 How we'd do it in Spring (and why Go won't play along)

【畫面】Split screen: left, `@Transactional public Order checkout(...)` and a `findByIdForUpdate` with `@Lock(PESSIMISTIC_WRITE)`. Right, an empty `orders.go`.

> If you're coming from Java, this evening goes like this.
> Put `@Transactional` on the service method. Spring opens the transaction before your method and commits after it, or rolls back if an exception flies out. For the lock, add `@Lock(LockModeType.PESSIMISTIC_WRITE)` to the repository query. C# folks: `TransactionScope`, or `SaveChanges` inside a `DbContext` transaction, and `FromSqlRaw` with `UPDLOCK`.
> Notice what you didn't write. The `Begin`, the `Commit`, the `Rollback`. A proxy wrote them for you, around your method, where you can't see it.

> Sure, that's convenient. But it hides the one thing this incident is about: **where the transaction starts and where it ends.** Put the stock check outside the annotation by accident, and you've built a very polite oversell machine. Who reads their own proxy stack trace?

> Go has no annotation, no proxy, no scope object. So the boundary is three lines, written where you can see them. Let's look.

## 3:30 Part one: the bug, as a test

【畫面】`internal/repository/orders_integration_test.go`, `naiveOrders.Place`.

> First, the bug. We don't describe it. We replay it. This is `naiveOrders`, a test-only version of the old code: select the stock, check it in Go, write the new number back.
> It even opens a transaction. Doesn't matter. A plain `SELECT` takes no lock. Twenty buyers all read "1", all pass the check, all write "0".
> We run it. One monitor in stock. **Six sold.** That test passes, which means the bug is reproduced, on demand, in about five seconds.
> The pause between the read and the write is only there to make the race certain instead of likely. The bug is the shape of the code, not the pause.

## 5:30 Part two: the fix, three lines you can see

【畫面】`internal/repository/orders.go`, `Place`, circling `Begin`, the `defer`, and `Commit`.

```go
tx, err := r.db.Begin(ctx)
if err != nil { ... }
defer func() { _ = tx.Rollback(ctx) }()
// ... lock, check, decrease, insert ...
return order, tx.Commit(ctx)
```

> Here's the whole transaction. `Begin`. Then straight away, `defer tx.Rollback`. Then the work. Then `Commit`.
> The deferred rollback is the trick. If any line in between returns an error, the function exits, and the deferred rollback undoes everything. If we reach `Commit`, the transaction is closed, and the rollback becomes a harmless no-op. One pattern, no try/catch, no `finally`.
> Java folks: it's `try`/`finally` that you write once, at the top, and never forget, because `defer` runs on every exit path.

【畫面】`db/queries/products.sql`, `LockProduct`, circling `FOR UPDATE`.

> And the lock. `SELECT id, price_twd, stock FROM products WHERE id = $1 FOR UPDATE`. That last word is the whole fix.
> It locks the row until the transaction ends. The second buyer reaches that line and waits. The first commits, stock is zero, the second gets the lock, reads zero, and gets an out-of-stock error. The check and the write are now one indivisible step.
> Sure, you could do `UPDATE ... SET stock = stock - 1 WHERE stock >= 1` and skip the lock for one product. For a single row, that's honestly a fine answer. But an order has many lines, and rules, and a price read at the same moment. The lock lets us read, decide and write in plain Go.

【畫面】`sort.Slice` on the lines.

> One more detail. We sort the lines by product id before locking. Two orders that want the same products in opposite order would each hold one lock and wait for the other: a deadlock. Sorted, they queue up instead. There's a test for exactly that.

## 8:30 Part three: all or nothing, and where the rules live

【畫面】`TestOrders_FailedOrderRollsBackEverything`.

> The other half of a transaction is "nothing". Test: an order with two lines. The first line, ten keyboards, is fine. The second, two monitors, is not. We expect an error, and we expect the keyboards back on the shelf.
> Ten keyboards in stock before. Ten after. The deferred rollback did its job.

【畫面】`service.OrderStore` and `repository.Orders`; `service.CheckoutCart` and `repository.Carts`.

> And the interfaces. The order service declares what it needs: `OrderStore`, one method, `Place`. And `CheckoutCart`, two methods, read the cart and remove from it. `repository.Orders` and our Redis `Carts` from last episode satisfy them without being told. The test's naive store satisfies `OrderStore` too, which is how we swapped in the bug to replay it. Implicit interfaces, doing their job.
> The service turns errors into its own: out of stock, product gone. The handler turns those into a `409` and a `404`. The database error with the IP address in it? That stays a plain `500`, and the client never sees it.

## 11:45 Three takeaways

> Let's wrap up.
> **One:** in Go, a transaction is `Begin`, `defer tx.Rollback`, `Commit`. No annotation, no proxy. The boundary is on screen, where you can read it.
> **Two:** "check, then write" is a race unless something holds a lock between the two. `SELECT ... FOR UPDATE` holds it for the length of the transaction. Lock in a fixed order, and keep the transaction short.
> **Three:** reproduce the bug before you fix it. A test that oversells on demand is worth more than a fix you believe in.
>
> The boss's next message: "Customers are asking for their money to actually move."
> Next episode: **payment.**
> Ship it small, ship it tested. See you at the next incident.

## Appendix B: open questions

- Checkout is not idempotent: a double-click or a retry after a timeout would buy the cart twice (once the cart is emptied it cannot, but if emptying fails the order is still placed and only a warning is logged). An idempotency key belongs with payment (episode 7).
- No payment, address or reservation timeout: stock is taken at checkout and never given back.
- The "six sold" number in Part one varies per run (it depends on the connection pool size); say "more than one".
- The naive store is test-only on purpose; the shipped code never contains the bug. To show it on the real server, record the test, not k6.
- `READ COMMITTED` (Postgres default) plus `FOR UPDATE` is enough here; `SERIALIZABLE` would also work but needs retry loops. Not mentioned in the script.
- The CHECK constraint on stock is the safety net, not the fix; the script mentions it only in passing, via the test comment.
- The sign-off is the fixed line from §6.1.
