# 第 8 集｜信沒寄出（口播稿草稿 v0）

- 目標長度：12–13 分鐘（約 3,500 字口播）
- 本集唯一主概念：**outbox pattern + 自己管生命週期的 goroutine**：下單時，「要寄一封信」這件事跟訂單寫在同一個資料庫交易裡；背景 goroutine 之後再把它撈出來寄，失敗就重試。goroutine 沒有 `Task` 可以 await，所以誰啟動它，誰負責取消它、等它結束
- 程式對應：tag `ep08`（`git checkout ep08`）
- 風格依 [style-guide.md](../style-guide.md)；【畫面】是剪輯提示，不唸出來。

## 0:50 時間錨點開場

> 現在是晚上 10 點 12 分，距離客服第一通訊息過了七分鐘，信箱裡躺著三十七位等不到信的客人。
> 今天做三件事：把「要寄信」這件事跟訂單寫在同一個交易裡；開一個背景 goroutine 把它撈出來寄，寄不成就重試；最後證明兩件事：寄信失敗會重試，下單回滾的話，連「要寄信」的紀錄也不會留下。
> 今天只學一個重點：**在 Go，goroutine 啟動之後沒有人幫你收；你要自己決定它什麼時候停，也要自己等它真的停了。**

## 1:40 C# 會怎麼寫（為什麼在 Go 行不通）

【畫面】左邊 ASP.NET Core：`await db.SaveChangesAsync(); await mailer.SendAsync(order);`，或是 `_ = Task.Run(() => mailer.SendAsync(order));`。右邊是空的 `outbox.go`。

> C# 的朋友，你大概有兩種寫法。第一種：`SaveChanges` 之後 `await` 寄信。寄信失敗了怎麼辦？訂單已經存了，你不能回滾；回客人錯誤，他會再下一次單。Java 的朋友換成 `@Transactional` 方法裡呼叫 `mailSender.send`：交易還開著、鎖還握著，你在鎖裡面打一通網路電話。
> 第二種：`Task.Run` 丟出去不管。進程在那一秒被重啟，信就憑空消失，連紀錄都沒有。
> 當然，你可以接 Hangfire，或是 Spring 的 `@Async` 加 `@Retryable`。可是它們都在解「寄信怎麼重試」，沒有解更根本的問題：**「訂單存了」和「信要寄」是兩件事，中間那一刻，進程隨時可能死。**
> 這個問題的名字叫雙寫（dual write）：同時寫兩個地方，沒有任何東西保證兩個都成功。

> Go 也一樣。所以我們要換個想法：不寫兩個地方，只寫一個。

## 3:30 第一段：把「要寄信」寫進同一個交易

【畫面】`db/migrations/00005_add_outbox.sql`，圈出 `payload jsonb`、`sent_at timestamptz`、`attempts`。

> outbox 的意思是「寄件匣」。一張資料表，每一列是「某件事等著被做」。我們的欄位：主題、內容（JSON）、嘗試次數、下次可以試的時間、寄出時間、最後一次的錯誤。

【畫面】`internal/repository/orders.go`，`Place` 的最後幾行。

```go
payload, err := confirmationPayload(order)
// ...
if err := q.InsertOutbox(ctx, dbgen.InsertOutboxParams{Topic: TopicOrderConfirmation, Payload: payload}); err != nil {
    return Order{}, fmt.Errorf("insert outbox: %w", err)
}
if err := tx.Commit(ctx); err != nil {
```

> 重點是這一行 `InsertOutbox` 的位置：**就在 `Commit` 前面，用的是同一個 `tx`**。第 6 集學的 `Begin` 加 `defer Rollback`，這裡直接用上。訂單、訂單明細、寄件匣這一列，三件事同生共死：全部成功，或全部沒發生。
> 我們沒有在這裡寄信。下單的路徑上沒有網路呼叫，寄信服務掛十分鐘，下單一毫秒都不受影響。
> 而且不管進程在哪一秒死掉，都不會出現「訂單存了，但沒有任何人記得要寄信」。信的承諾，跟訂單同時存在。

## 5:45 第二段：背景 goroutine 撈出來寄

【畫面】`internal/service/outbox.go`，上面是 `Mailer` 介面。

```go
type Mailer interface {
    SendOrderConfirmation(ctx context.Context, orderID, totalTWD int) error
}
```

> 先看介面。`Mailer` 只有一個方法，而且**它定義在用它的人旁邊**，不是定義在寄信程式碼旁邊。真的寄信的、只會印日誌的、測試用的假的，都只是剛好有這個方法。沒有 `implements`。C# 的朋友，你可以把它想成 `IMailer` 住在 consumer 的專案裡，不是住在 SMTP 的專案裡。

【畫面】`repository/outbox.go`，`Dispatch`，圈出 `FOR UPDATE SKIP LOCKED`（`db/queries/outbox.sql`）。

> 撈信的 SQL 有一個你可能沒見過的尾巴：`FOR UPDATE SKIP LOCKED`。意思是：這幾列我先鎖了，別人看到被鎖的就跳過，不要等、也不要重複寄。就算以後開兩個 worker，同一封信也只會被一個人拿到。
> 寄成功，標 `sent_at`；寄失敗，`attempts` 加一、記下錯誤、算出「多久之後再試」，一秒、兩秒、四秒，最多五分鐘。試了八次還不行，就留在表裡等人處理，不再自己重試。

【畫面】`OutboxDispatcher.Run`。

```go
func (d *OutboxDispatcher) Run(ctx context.Context) {
    ticker := time.NewTicker(d.cfg.Interval)
    defer ticker.Stop()
    for {
        d.RunOnce(ctx)
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
        }
    }
}
```

> 然後是 goroutine 本人。這個迴圈用 `time.Ticker` 每隔一段時間看一次；`select` 同時等兩件事：時間到了，或是 `ctx` 被取消了。取消了就 `return`。
> 注意 `Run` 自己是**阻塞**的，它沒有開 goroutine。為什麼？因為「要不要在背景跑」是呼叫端的決定。

## 8:20 第三段：誰啟動，誰負責收

【畫面】`cmd/api/main.go`，圈出 `workerCtx, stopWorker := context.WithCancel(ctx)` 與 `<-workerDone`。

```go
workerCtx, stopWorker := context.WithCancel(ctx)
workerDone := make(chan struct{})
go func() {
    defer close(workerDone)
    dispatcher.Run(workerCtx)
}()
defer func() {
    stopWorker()
    <-workerDone
}()
```

> C# 的朋友，這是這一集最大的差別。你的 `Task` 是一個東西：你拿著它，可以 `await`，可以丟 `CancellationToken`，丟完它會告訴你結果。Go 的 `go` 關鍵字**不回傳任何東西**。你按下去，goroutine 就自己在那邊跑了，沒有人拿著它的把手。
> 沒有把手，就要自己做一個。我們做了兩個：`context` 負責「叫它停」；一個 channel 負責「它真的停了」。`defer close(workerDone)` 是 goroutine 離開前最後一句話。
> 主程式結束前，先 `stopWorker()`，再 `<-workerDone` 等它。這段 `defer` 寫在 `pool.Close` 的後面，所以先跑：worker 一定在連線池關掉之前結束。反過來的話，worker 會對著一個已經關掉的資料庫庫存，在背景默默報錯。
> 如果你忘了等，會怎樣？程式照樣會結束，只是有人在寄信的途中被腰斬。我們的寫法在這裡有一個小心思：寄完信之後，「已寄出」這個標記，用 `context.WithoutCancel` 寫進去，就算正在關機也要寫成功，不然下次啟動又寄一次。

> 最後，我們把真正的寄信服務換成一個只印日誌的 `logMailer`：目前商店還沒有客人帳號，也沒有客人的 email，所以先寫「我會寄」。真的寄信、真的收件人，留給後面。

## 10:00 證明：寄信失敗會重試；回滾不留紀錄

【畫面】`go test -tags=integration ./internal/repository -run Outbox -v` 全綠。

> 先看第一個測試，`TestOutbox_FailedSendIsRetriedUntilItWorks`。測試用的寄信器前兩次都失敗，第三次成功。worker 每五毫秒看一次，等待時間設成零，所以不用等。結果：寄信器被呼叫三次，`attempts` 是三，最後一次的錯誤被清掉，`sent_at` 有值。再跑一輪，寄信器不會被呼叫第四次：寄出去的，不會寄兩次。
> 測試最後有一行：`cancel()`，然後 `<-done`。**先確定 worker 真的停了，才去看最後的狀態**，不然測試自己就是一個沒人收的 goroutine。
> 第二個測試，`TestOutbox_RolledBackOrderLeavesNoOutboxRow`：我們包一個 `Commit` 一定失敗的交易，下一張單。結果：`outbox` 零列、`orders` 零列，庫存回到原本的 10。**信的承諾，跟著訂單一起被收回了。**
> 還有一個：寄信器永遠失敗，`MaxAttempts` 設三，跑六輪，寄信器只被叫了三次，那一列留著，上面寫著為什麼：`smtp down`。

> 單元測試用的是假的寄信器和假的 store：`Run` 在 `ctx` 取消後一定要回來，兩秒內沒回來測試就失敗。你的 goroutine 洩漏，在 CI 就會被抓到，不用等到上線。

> 現在是晚上 10 點 58 分。客服傳來：「剛剛那三十七位的信，補寄了。」
> 我說：「它們一直都在表裡，只是在等寄信服務醒來。」

## 11:45 三點收尾

> 好，我們收一下。
> **第一**，「存了訂單」和「寄信」是兩個寫入，沒有東西保證兩個都成功。把第二個寫成同一個交易裡的一列，就只剩一個寫入。
> **第二**，goroutine 沒有 `Task`。誰啟動它，誰就要用 `context` 叫它停、用 channel 等它真的停。
> **第三**，寄信失敗不是例外，是正常路徑：記下錯誤、算好下次、重試；而且要有一個上限。

## 附錄 B：待確認

- 商店目前沒有客人帳號與 email，所以收件人不存在；`logMailer` 只印日誌。口播不要暗示已經會寄真的信。
- 架構文件寫的是「outbox + NATS/RabbitMQ + worker」；本集只做資料庫輪詢的 worker，沒有訊息佇列。
- `Dispatch` 在寄信期間交易是開著的（為了 `FOR UPDATE SKIP LOCKED`）。寄信很慢的時候應該改成「先標記領取、再寄、再回寫」；本集量小，不處理。
- 語意是「至少一次」：寄出後、標記 `sent_at` 前進程死掉，下次會重寄一次。收件端要能容忍重複，這和第 7 集的冪等鍵是同一個主題，錄影不展開。
- 試滿 `MaxAttempts`（預設 8）的列不會自動再試，也沒有告警或人工重送工具。
- 退避時間用資料庫的 `now()` 算，與 Go 的時鐘無關。
- 本集沒有壓測，也沒有多 worker 同時跑的測試；`SKIP LOCKED` 的行為只靠 SQL 本身的語意，沒有測試證明。
