# 平實口播規範（v1）

這份規範管「平實口播版」的口播、主張清單與 Short。它取代 [style-guide.md](style-guide.md) 的幽默文案；舊文案與 `docs/scripts/` 留著對照，不再更新。

目標有兩個。第一，人聽一次就懂。第二，AI 或任何人能逐句查證：口播說的每一件「這個 repo 是這樣」的事，都有一條主張和一個可以執行的檢查。

## 1. 句子

1. **一句一主張**。一句話只說一件事。中文一句不超過 30 個字，英文一句不超過 20 個英文字（見第 6 節）。
2. **主詞寫明**。寫「`SetItem` 用 pipeline 送出兩個指令」，不寫「它會一次送出去」。
3. **數字寫全**。寫「期限是 7 天」「3 個方法」，不寫「一陣子」「幾個」。
4. **一物一名**。同一個東西整章用同一個名字。第一次出現的名詞用一句話定義。
5. **不用反話、諧音、反問**。這些句子無法逐句查證。**比喻每章最多一個**，而且必須是生活比喻（例：把兩台伺服器各有一份購物車，說成兩間分店各有一本帳）。比喻不是 repo 事實，不掛主張編號；說完比喻的下一句要回到 repo 事實。
6. **不點名真人**，不評論其他創作者或公司。
7. **程式名詞照原文唸**：`CartStore`、`go build`。畫面與字幕用同一個寫法。

## 2. 什麼要有主張編號

| 口播內容 | 做法 |
|---|---|
| 這個 repo 的事實（檔案、函式、行為、測試結果） | 掛 `C<章>-<號>`，主張清單裡要有機器檢查 |
| 其他語言或框架的對照（C#、Java） | 掛 `X<章>-<號>`，每一種語言各附一個官方文件來源 |
| 事故情境（客服訊息、時刻、對話） | 不掛編號。第一句要說「事故情境是這樣」，並由一個測試或壓測重現，重現的那一句掛 `C` |
| 下一章預告 | 不掛編號。只說下一章的標題與事故情境，不說數字結論 |
| 串場句（「先看原因」「接著看修法」） | 不掛編號 |
| 生活比喻（每章最多一個） | 不掛編號。不是 repo 事實，所以不能拿來當證據；下一句回到事實 |

口播不唸行號。行號只放在畫面上，由產線從 tag 的程式碼取出，不會寫錯。

終端機畫面的輸出要貼真的。畫面放不下時，明寫「畫面省略中間 N 行」。

## 3. 主張清單怎麼寫

格式見 [claims/README.md](claims/README.md)。寫的時候守這幾條：

1. **檢查不能比主張弱**。主張說「三個方法」，檢查就要對到三個方法，不能只查到型別名字。
2. **說「沒有」要查「沒有」**。用 `git grep -q` 加 `exit: nonzero`，或 `git cat-file -e` 加 `exit: nonzero`。
3. **說「改掉就壞」要真的改**。用 `edit` 改一處，再檢查編譯或測試失敗，並比對錯誤訊息。
4. **說「測試證明」要真的跑**。用 `run` 執行那一個測試，並比對 `--- PASS: <測試名>`。需要 Docker 的加 `requires: ["docker"]`。
5. **跨章比較**用 `git diff --quiet <前一個 tag> <這個 tag> -- <檔>` 或 `git grep -q -e <字> <tag> -- <檔>`。
6. 主張本文中英文各一句，意思相同。

寫完跑 `go run ./cmd/claimcheck docs/claims/chNN.json`，要全部 `PASS`（`reference` 顯示 `REF`）。

## 4. 長片的一章（8–10 分鐘）

一個系列做成一支分章節的長片，各章是長片裡的章節（YouTube 章節時間戳），章不單獨上傳。

每章的配音總長要落在 **8 到 10 分鐘**（480 到 600 秒，兩端都算）。產線在 `captions` 步驟檢查，超出就失敗。這個範圍約等於 1,500 到 1,900 個英文字。

四拍，順序固定：

1. **事故**：章名、對應的 tag、開始前的狀態、事故情境。
2. **原因**：為什麼會發生，指到程式碼。
3. **修法**：這一章加了什麼，一次講一個改動，每個改動配一段程式碼。
4. **證明**：哪個測試或壓測證明修好，以及怎麼自己跑 `make claims`。

口播結構：

1. **長片開場 15 秒內講痛點**。第一句就說客人遇到什麼事，不先介紹頻道或系列。
2. **每章先錯再對**。先跑錯的寫法、讓觀眾看到壞掉的結果，再改成正解。
3. **每個功能跑一次看結果**。每做完一個功能，就執行一次，把真實輸出放在畫面上（見第 2 節，輸出要貼真的）。
4. **每章最多一個生活比喻**，規則見第 1 節第 5 條。
5. **長片結尾依序是回顧、限制、下一步**。回顧：這支片做了什麼。限制：這個做法不處理什麼。下一步：下一個系列或下一章要解的事故。
6. **不放贊助段**。
7. **語言對照以 C# 為主、Java 為輔**。有真正對應的概念才對照，每一種語言掛 `X<章>-<號>`（見第 2 節）。

每章結尾三句：這一章的三個重點、對應的 tag、下一章的標題。

## 5. Short（45 秒以內，直式 1080×1920）

三拍加導流：事故一句、原因一段、修法一段、證明一句，最後一句說「完整說明在長片第 N 章」。Short 的用途是推廣長片：每支 Short 講一個事故，結尾指向長片的對應章節。

- 5 到 7 段，全片口播約 100 個英文字。
- 程式碼畫面最多一個，不超過 6 行。
- 只用長片那一章已經有的主張編號，不新增主張。
- **燒英文字幕**在畫面上，**另附中文 CC**（`.zh.srt`）。長片則不燒字幕，上傳英文與中文兩條 CC。
- 說明欄放長片連結的欄位（網址由作者上傳長片後填）。

## 6. 英文是正本，中文是逐句翻譯

英文口播是唯一正本。分鏡每段同時存 `en` 與 `zh`：

```json
"narration": { "en": "The cart lives in the memory of the API process.", "zh": "購物車存在 API 程式的記憶體裡。" }
```

1. **en 先寫，zh 照 en 翻**。主張編號、事故劇情、時序都以 en 為準；改了 en，同一段的 zh 一起改。
2. **句數必須相同**。en 與 zh 切句後的句數要一樣，第 N 句 en 對第 N 句 zh。不一樣，產線會失敗並指出是哪一段。英文在 `. ! ?` 後面接大寫字母、數字或引號時切句，中文在 `。！？` 後切句，所以英文句中不要用會被誤切的縮寫（例如 `e.g. The`）。
3. **只配英文**。配音用本地 Kokoro-82M、聲音 `af_heart`，只讀 en。中文是字幕，不配音。
4. **每句上限**：英文每句不超過 **20 個英文字**，中文每句不超過 **30 個字**。超過就拆句。產線會檢查，超過就失敗。
5. **念法與寫法分開**。字幕與逐字稿照原寫法（`C#`、`ep05`）。送給配音的文字另外過一張念法對照表（`config/pronunciation.json`，在影片產線 repo）：`C#` 念 `C sharp`、`ep05` 念 `ep-05`。口播裡出現新的程式名詞唸不對時，加規則到對照表，不要改口播寫法去遷就配音。產線會用語音辨識把配音轉回文字，與原稿比對，念錯的句子會被列出來。
6. 規則 1 到 7（第 1 節）在英文照用：一句一主張、主詞寫明、數字寫全、一物一名、不點名真人。
7. 長片字幕是英文與中文兩條 CC，每一句的時間相同。Short 燒英文字幕、另附中文 CC。

英文口播的語言對照以 C# 為主、Java 為輔，中文版同一份口播的對照一樣以 C# 為主。
